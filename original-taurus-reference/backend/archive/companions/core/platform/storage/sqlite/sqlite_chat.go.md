# sqlite_chat.go

The agent-chat slice of the SQLite `Store`. Three tables back it: `agent_chats`
holds the conversation container (title, mode, the resource it hangs off, the
persona currently answering), `agent_chat_turns` holds the append-only message
log, and `agent_chat_attachments` holds files and directory-manifest entries
bound to a chat.

Unlike agent tasks, chats are stored as ordinary columns rather than JSON
documents — the data is flat, so every field gets its own column and the scan
helpers map rows straight onto the `chat` capability's types. This file is part
of the one shared `*Store` and connection; the split from `sqlite.go` mirrors
`core/capability/chat`.

## Code breakdown

### File header and imports

The package comment records the organizational split. Imports are minimal —
`database/sql` and `errors` for `sql.ErrNoRows` matching, `time` for timestamp
parsing, and the `chat` capability for the domain types and `chat.ErrNotFound`.
Note that several methods shadow the package name with a `chat` parameter; the
package identifier is still reachable in the helpers that need it.

### CreateChat — insert the container

A single flat insert of the chat's columns, with both timestamps formatted
through the shared `timeLayout`. There is no uniqueness translation here: chat
ids are generated by the caller, so a collision is an internal error and is left
to surface as the raw driver error.

### ChatByID and scanChat

`ChatByID` selects one row and hands it to `scanChat`, which is typed against the
package's `rowScanner` interface so the same routine serves the single-row and
listing paths. It maps `sql.ErrNoRows` to `chat.ErrNotFound` and parses the two
stored timestamps, deliberately ignoring parse errors so a malformed timestamp
degrades to a zero time rather than failing the whole read.

`ChatByID` takes the project id as its first parameter and filters on it —
`WHERE id = ? AND project_id = ?` — so a chat owned by another project reads as
`chat.ErrNotFound` rather than being returned for the caller to vet. This
finishes DEF-1 for chats, extending the in-SQL scoping record 0115 introduced for
the file store. The `Chats` service still compares `ProjectID` after loading and
returns `ErrProjectScope`; that check stays deliberately, as a second independent
layer for any store that does not scope. In practice the SQL now answers first,
so cross-project access surfaces as `ErrNotFound` — which the chat handler
already maps to the same 404 as `ErrProjectScope`, leaving the HTTP contract
unchanged. `id` is the primary key, so the extra predicate is a filter on the
single row the unique index already found.

### ChatsByProject — listing, optionally narrowed to one resource

The one place in the file that builds SQL dynamically. The base query filters by
project; when `resourceID` is non-empty an extra predicate and argument are
appended, so the same method serves both "all chats in this project" and "chats
attached to this document/resource". The clauses are appended in a fixed order
with placeholders — the arguments stay parameterized, nothing is interpolated:

```go
query += ` AND resource_id = ?`
args = append(args, resourceID)
```

Results are ordered `updated_at DESC`, which pairs with `TouchChat` below to give
a most-recently-active-first list.

### AppendTurn — the message log grows only at the end

Inserts one turn row. There is no update or delete counterpart in this file: the
turn log is append-only, so a conversation's history is whatever was written, in
the order it was written. The optional `task_id` links a turn to the agent task
that produced it.

### TurnsByChat — replay in insertion order

Reads a chat's turns ordered by `rowid` rather than by `created_at`. That is the
important detail: `rowid` is SQLite's monotonic insertion counter, so two turns
written within the same timestamp resolution still replay in the exact order they
were appended — which a `created_at` sort could not guarantee. The scan is done
inline rather than through a helper, since nothing else reads turns.

### TouchChat — bump activity without touching content

Sets `updated_at` on a chat. Called when a chat gains a turn, so `ChatsByProject`
can order by recency; keeping it separate from `AppendTurn` lets other events
mark a chat active too.

### SetChatPersona — repoint the answering persona

Updates `persona_id` for one chat and checks `RowsAffected`: zero rows means the
chat does not exist, reported as `chat.ErrNotFound` rather than passing silently.
This is the only mutation of a chat container's own fields besides the timestamp
bump, which keeps the container effectively immutable apart from persona and
activity.

### CreateChatAttachment and ChatAttachmentsByChat

Attachments cover two shapes in one table, discriminated by `kind`: a plain file
(`file_id` points at stored content) and a member of an uploaded directory
(`relative_path` and `directory_upload_id` place it within its manifest). A
single table keeps a chat's attachment list a single ordered query rather than a
join across two shapes. The listing orders by `created_at, id`, with `id` as the
tiebreaker so attachments uploaded in the same instant still have a stable,
deterministic order.

### ChatAttachmentByID, DeleteChatAttachment, and scanChatAttachment

`ChatAttachmentByID` is the single-row lookup; `scanChatAttachment` maps
`sql.ErrNoRows` to `chat.ErrNotFound` and parses `created_at`, mirroring
`scanChat`, and takes the package's named `rowScanner` like its siblings. It is
project-scoped for the same reason `ChatByID` is, and in the same shape: the
project id is the first parameter and joins the `WHERE` clause, so an attachment
in another project is `chat.ErrNotFound`. `DeleteAttachment` in the capability
still checks both `ProjectID` and `ChatID` on the loaded record — kept as the
redundant second layer, not removed.
`DeleteChatAttachment` is unconditional and does not check `RowsAffected`:
deleting an attachment that is already gone is treated as success, so the removal
is idempotent.
