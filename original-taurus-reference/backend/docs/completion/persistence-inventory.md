# Persistence and migration inventory

The shipped store is one SQLite database opened by
`core/platform/storage/sqlite.Open`. Schema creation, additive compatibility
migrations, data backfills, and repair steps run at startup. This inventory
freezes the physical schema and assigns every table to an owner and completion
contract. The index list includes both named schema indexes and SQLite's
automatic primary-key/unique-constraint indexes.

The executable test compares a fresh database with a representative legacy
database that contains a real row before startup migration. Exact normalized
schema convergence and fixture preservation are both required. This is a
representative upgrade check, not a claim that every historical database shape
has a fixture.

Current migration facts:

- An old pre-KLR `knowledge_nodes` shape is dropped because it is derived and
  rebuilt. Separately, databases with `PRAGMA user_version < 1` have Document,
  ChangeSet, history, anchor, comment, and reply rows deleted by the historical
  block-kind reset before `user_version` advances to 1. That pre-existing
  dev-stage reset is irreversible and is a production migration/restore risk
  owned by Ω-042 and Ω-044.
- Schema statements use `CREATE ... IF NOT EXISTS`, followed by additive
  `ALTER TABLE` compatibility steps that tolerate duplicate-column errors.
- Resumable backfills cover document history, vector BLOBs, knowledge-window
  text/block coverage, source metadata, and visible timestamps.
- The now-unused whole-source knowledge text is blanked only after window and
  source metadata backfills establish the replacement representation.
- Startup migration has no numbered migration ledger, downgrade path, or
  production multi-instance migration coordinator. Those remain owned by
  Ω-042.
- SQLite is the only durable application store today. Inline file content and
  derived vector/index BLOBs are explicitly called out below rather than
  silently treated as a production object-storage boundary.

Document head revisions, and repairs visible timestamps. The acceptance script
pins the 44-statement count; the fresh/upgrade test pins final convergence and
fixture preservation.
