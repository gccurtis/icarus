Activity inspector · proposed design

Make Activity own its vocabulary.

Producers should submit typed events with structured facts. Activity should validate them and derive What, Where, and detail consistently for every consumer.

01

The boundary

One Activity capability, one closed event catalog

Expose a transaction-aware recorder through the Activity capability index. Each producer passes an existing Store unit of work, trusted project/actor scope, and one discriminated event. The capability constructs and validates the stored row.

ProducerrenameExternalFile

Knows the mutation-specific facts: ID, old name, new name, and paths.

Typed eventexternal-file.renamed

Carries fields required by that exact event and no display prose.

Activity capabilityrecordActivity(unit, scope, event)

Builds snapshots, admits the schema, and writes through the supplied transaction.

Shared projectionformatActivity(event)

Derives one title, detail, target, and destination for all views.

Why it must accept the existing transaction

A standalone remote “record activity” call could commit history after the originating change fails, or lose history after the change succeeds. External-file state and its activity must remain one atomic Store intent.

03

Example contract

type
"external-file.renamed"
file
{ id, previousName, name }
location
{ previousPath, path }
actor
Derived from trusted capability scope; never accepted as client proof.
presentation
Derived centrally as “Renamed ‘old.csv’ to ‘new.csv’.” Consumers do not reinterpret the event.
destination
External Files singleton with the exact current file selected; unavailable copy after deletion.

Keep historical snapshots

IDs enable current navigation. Names and paths preserve what the event meant when the target has changed or disappeared.

Keep the catalog closed

Producer call sites cannot submit arbitrary verbs. Adding an event requires its payload, validation, formatting, and destination behavior together.

05

Implementation sequence

  1. Define activity events

    Add the discriminated event union, target builders, payload validation, and shared presentation model under the Activity capability.

  2. Move live producers

    Convert External Files within its existing transactions. Record the initial Agents task start and its completion as typed events; remove status-as-verb.

  3. Unify consumers

    Move Overview, History, Activity, Person, Agents, resource details, and External Files history onto the same formatter and destination rules.

  4. Replace fixtures

    Seed only typed events a live producer can emit. It is acceptable for categories without real writers to have no activity.

  5. Verify the boundary

    Test schema rejection, transaction rollback, project scope, deleted-target snapshots, consistent presentation, and Chromium navigation.

06

Settled scope

  • Research Chat and prompt blocks do not produce Activity events.
  • Agents tasks produce one initial-start event and one completion event.
  • Retention remains a future database/storage policy rather than application configuration for the JSON Store.

The proposed event catalog is now settled for the persistence implementation.
