# Frontend Architecture

## Goal

The Icarus frontend is an Eclipse Theia browser application written in TypeScript and React. Theia provides the workbench shell—panels, commands, menus, keybindings, layout, and extension points—while Icarus owns its product features and visual language.

There is no Electron target. The optional `node/` side of a Theia extension is part of the workbench host; it must not contain Icarus backend capabilities or canonical project state.

## Directory template

```text
frontend/
├── application/
│   ├── package.json                  # Theia browser product composition
│   ├── src-gen/                      # Generated by Theia; never hand-edited
│   └── test/
└── extension/
    ├── package.json
    ├── src/
    │   ├── browser/
    │   │   ├── shell/                # Global commands, layout, navigation
    │   │   ├── features/             # User-facing product areas
    │   │   ├── components/           # Carbon adapters and Icarus compositions
    │   │   │   ├── carbon/           # Central wrappers/defaults when needed
    │   │   │   └── composites/       # Product-specific combinations
    │   │   ├── data/                 # Supabase/API clients and query keys
    │   │   ├── state/                # Ephemeral frontend-only state
    │   │   └── styles/               # The only global styling authority
    │   │       ├── tokens.css
    │   │       ├── typography.css
    │   │       ├── tailwind.css
    │   │       ├── carbon.scss
    │   │       ├── index.css
    │   │       └── themes/
    │   │           ├── celestial.css
    │   │           └── eclipse.css
    │   ├── common/                    # Browser/host protocol values only
    │   └── node/                      # Optional Theia host integration
    └── test/
```

Start with one custom Icarus extension. Split it only after a concrete independent distribution or lifecycle boundary appears. A package per feature would recreate the complexity this architecture is meant to remove.

## Feature template

```text
features/<feature>/
├── index.ts                          # Feature's narrow public surface
├── contribution.ts                   # Theia commands, menus, bindings, widgets
├── model.ts                          # Frontend presentation state
├── data.ts                           # Queries and mutations used by the feature
├── views/                            # Feature-owned React views
└── test/
```

A feature may use multiple backend capabilities. It must not reproduce capability rules. Feature-private components remain beside the feature; only components used across features move into `components/`.

## Component template

```text
components/<component>/
├── <Component>.tsx
├── <Component>.test.tsx
├── <Component>.css                   # Token references only
└── index.ts
```

Choose UI building blocks in this order:

1. Use an existing Theia workbench primitive when it is part of the shell.
2. Use an IBM Carbon component for standard application UI such as accordions, buttons, forms, tables, modals, tabs, menus, notifications, tooltips, and tree views.
3. Compose Carbon components into an Icarus-specific component when the product needs a domain-specific interaction.
4. Build a new primitive only when neither Theia nor Carbon provides the required behavior, and record that gap in the component documentation.

Carbon is the canonical application component library. Icarus does not build generic controls that Carbon already owns. Carbon is still not Icarus's theme owner: Web Awesome is not part of the selected stack, and Carbon's default visual theme is replaced by the centralized Icarus token bridge.

This division is the chain of responsibility:

| Concern | Owner |
| --- | --- |
| Workbench frames, docking, commands, menus, and editor lifecycle | Eclipse Theia |
| Standard controls, component behavior, and component accessibility | IBM Carbon React |
| Colors, typography, spacing, radii, elevation, and motion | Icarus design tokens |
| Product-specific combinations and data behavior | Icarus features and composites |

## Styling authority

Icarus owns its visual system. The approach follows the strongest part of Taurus Alpha: a small, centralized token surface with all product styling derived from it.

`tokens.css` is the only place raw design values may be declared. It contains:

- typography families, sizes, weights, and line heights;
- semantic surfaces and text colors;
- borders, focus, selection, status, and data colors;
- a fixed spacing scale;
- radii and elevation;
- motion durations and easing;
- shell dimensions and z-index layers.

Theme files assign values to the semantic color tokens. Components consume semantic names such as `--surface-canvas`, `--text-primary`, or `--border-subtle`; they do not consume palette steps or raw hex values.

```css
:root {
  --font-sans: "IBM Plex Sans", sans-serif;
  --font-mono: "IBM Plex Mono", monospace;
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --radius-control: 0.25rem;
  --motion-fast: 120ms;
}

[data-icarus-theme="celestial"] {
  --surface-canvas: #f7f8fb;
  --text-primary: #161616;
  --border-subtle: #dfe3ea;
  --action-primary: #0f62fe;
}
```

The exact values above are illustrative; the approved token set is copied and refined from `original-taurus-reference/frontend/src/app.css`, not invented ad hoc inside features.

### Tailwind

Tailwind is a token-bound layout and utility tool. Its theme maps to Icarus CSS variables. Arbitrary colors, fonts, radii, shadows, and spacing values are prohibited in feature code. If a value is truly reusable, it is added to the token contract first.

### IBM Carbon

Carbon React is the default for standard application controls. Its documented component catalog covers the ordinary gaps we are specifically trying to avoid rebuilding, including accordions, data tables, forms, modals, pagination, popovers, tabs, tooltips, file upload, and tree views. `carbon.scss` is the single bridge from Icarus tokens into Carbon theme and component variables. We do not treat Carbon's stock theme as an independent source of design values or allow feature code to override it locally.

A central adapter in `components/carbon/` is allowed only when Icarus must establish a repeated product default, add project-specific behavior, or isolate a feature-flagged Carbon API. It must remain a thin wrapper. We do not wrap every Carbon component merely to rename it.

### Icons

Carbon components retain their expected operational icons so their behavior remains internally consistent. Lucide is reserved for Icarus domain concepts and product actions outside those component internals. Icons are imported by name, never through dynamic package-wide loading. This boundary prevents two icon sets from competing for the same role.

## Planned frontend libraries

| Library | Purpose | Boundary |
| --- | --- | --- |
| Eclipse Theia | Browser workbench, widgets, commands, layout, extension model | Shell only; not domain logic |
| TypeScript + React | Product views and strongly typed client code | Frontend application and extension |
| IBM Carbon React | Canonical standard controls and accessible interaction behavior | Mapped through Icarus styling; not theme authority |
| Tailwind CSS v4 | Token-bound layout and utilities | No arbitrary design values in feature code |
| Lucide React | Default product icons | Named, tree-shaken imports |
| IBM Plex Sans / Mono | Self-hosted product typography | Loaded centrally, never per feature |
| `@supabase/supabase-js` | Authenticated reads, realtime, storage, and allowed mutations | RLS remains authoritative |
| TanStack Query | Server-state caching, invalidation, and refetch | No canonical project state in client memory |
| Vitest + Testing Library | Unit and component tests | Tests behavior and accessibility |
| Playwright | Browser and cross-system flows | Root end-to-end suite |

Carbon's official React catalog is the first stop for any ordinary application component. No rich-text editor, diagramming toolkit, spreadsheet engine, or other feature-specific framework is selected until the corresponding capability is designed and its requirements are known.

## Data and state rules

- Supabase and backend capability procedures own canonical project state.
- TanStack Query owns cached server state and invalidation.
- `state/` owns only ephemeral presentation state such as a selected tab or temporary panel state.
- Private realtime topics carry project-scoped change facts. They invalidate and refetch authoritative queries rather than reproducing a second database in the frontend.
- Optimistic updates are allowed only when failure can be cleanly rolled back.

## Frontend definition of done

A new feature is complete only when it has:

1. a clear Theia contribution and navigation entry;
2. project-scoped data access through an existing capability contract;
3. token-only styling and both approved themes;
4. keyboard and screen-reader behavior;
5. loading, empty, error, and reconnect states;
6. component tests and an end-to-end path for its critical behavior.
