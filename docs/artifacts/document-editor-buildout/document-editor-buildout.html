Document Editor Buildout

The surface types and saves. Nothing it types has any formatting, because the schema declares no marks, the translator emits no mark ops, and the applier refuses everything but a row proportion. Section 02 draws the goal state — the surface and eleven panels. The rest is the order in which we get there, and the four decisions I need from you before we start.

Read against work/semantic-overlay-cutover Editor ProseMirror 1.25, custom schema Built today 2 of 21 panels

01Where it actually stands

I ran it. A document opens, paginates onto Letter at 82 characters and 35 lines a page, splits and merges rows on Enter and Backspace, emits granular text ops, and says Saved. Selecting text lights the inspector's Text selection lens with a real quote and a real character count. Everything below that quote is a mock that writes nothing — the lens says so itself, in a collapsed section called Mock.

Winter readiness brief

Revised 4 February

Peak demand on the western interconnect is forecast to exceed last winter's record by four percent, and two of the three substations that carried that peak have since been derated. This brief sets out where the exposure sits, what it would cost to close, and which of those costs are already committed.

Where the exposure sits

Substation 14 is the binding constraint. Its transformer bank was derated in September after the oil analysis came back, and the two feeders that would otherwise pick up its load both run through the same corridor, so a fault on either leaves the northern ring supplied from one direction only.

The second concentration is behind the coastal tie. Nothing there has been derated, but the tie has carried an unplanned outage in each of the last three winters and the spares position for its breakers is one deep.

Recommendation

Bring the corridor reconductoring forward by one season and hold the derating until it lands. Everything else in this brief is contingent on that decision.

03Five things block everything else

Alignment, styles, spacing, multi-selection and comments all want the same five pieces, and none of them exists. Building any one feature first means building all five underneath it, so they are worth naming as their own phase.

1

The schema declares no marks and the block carries no attributes

text_block has blockId, atomId and share. There is no variant, no style key, no format, and the mark set is literally empty. Nothing can be bold inside the editor's own document, so nothing can be round-tripped out of it.

procedures/schema.ts

2

The translator has no vocabulary for anything but text and structure

translate emits five shapes: a text splice, a block insert, a block remove, a row insert/remove/move, and a set on row/proportions. A mark change produces no op at all.

procedures/translate.ts

3

The applier refuses anything it does not already know

applySet handles exactly one path — <rowId>/proportions — and calls refuse() for everything else. A perfectly formed mark op would be rejected by the server it was sent to.

capabilities/document/api/submit-document-changes/apply-ops.ts

4

The document runtime is not optimistic; the deck runtime is

buffer() appends ops and leaves runtime.body alone — the body only moves when sync re-reads the leader. Today that is invisible, because ProseMirror holds the optimistic text. The moment a panel edits something ProseMirror does not hold, the change disappears for two seconds and then comes back. The slide deck already solved this with a shared applier both sides run.

model/client/document-runtimes/methods/apply.ts · model/client/slide-deck-runtimes/methods/apply.ts

5

There is no op target for the document itself

DocumentOp targets are row · block · atom · mark. Page setup and the style set live on the body, above every row, and cannot be addressed. Both are things you asked to be able to edit.

representation/data/types/documents/op.ts

04One rule decides most of the rest

Anything inside a block is edited through ProseMirror. Anything outside a block is edited through the runtime.

Marks, variant, style key, alignment: a panel asks the editor to run a command, the transaction flows through the existing dispatch → bodyOf → translate pipeline, and the ops fall out the end. Page setup and the style set: a panel calls runtime.apply directly and the surface re-projects.

The reason is undo. Text undo is ProseMirror's history() plugin, bound to Mod-z in the content surface; DocumentRuntime carries a second, separate undo stack that nothing currently calls. If pressing B in the inspector pushed onto the runtime stack while typing pushed onto ProseMirror's, ⌘Z would walk two histories in an order nobody can predict. Routing in-block edits through ProseMirror keeps one stack and costs nothing — the pipeline already exists.

It also avoids a repaint. paint() builds a fresh EditorState and would drop the caret every time you pressed a formatting button. A ProseMirror command mutates in place and the selection survives.

How a panel reaches the editor

A view may not touch the runtime register — runtime-through-workspace-state greps the raw text of every view leaf for attach( — so the channel has to be on the workspace state. I would add one method to DocumentRuntime: the content surface registers its EditorView on mount, panels call runtime.command(...), and the surface runs it. One method, one direction, and the panel never learns what ProseMirror is.

05The op vocabulary, extended

Every new op below has to be emitted by translate and accepted by applyOps in the same change, or the client and the store disagree about what a document is. The path grammar stays <id>/<field> except for the document target, which has no id and uses a plain field path.

TargetOp and pathCarries
mark insert · remove
<blockId>/marks		 Whole Mark values by id. A mark is created when you first bold a range and removed when the last style comes off it.
mark set
<markId>/style · /color · /link · /from · /to		 Adding italic to a range that is already bold, recolouring, retargeting a link, or a range being extended by dragging.
block set
<blockId>/variant · /level · /style · /format		 Heading versus body, heading depth, which named style the block uses, and the block's own box — which is where alignment lives.
document new set
pageSetup · pageSetup/margins/top · styles/defaultKey		 Paper, orientation, each margin, and which style a new block gets.
document new insert · remove
styles		 Creating and deleting a named style. StyleSet.styles is a record, so the ids are its keys and after is documented as ignored.
document new set
styles/<key>/fontSize etc.		 Editing one field of one named style, so two people changing size and colour on the same style do not clobber each other.

Marks must not churn on every keystroke

A Mark is { id, from, to, style?, link?, color? } with from and to as UTF-16 offsets into the block's display string. Type one character at the start of a paragraph and every mark after it moves. If translate diffed mark arrays it would emit a set on from and to for every mark in the block, per keystroke.

The applier shifts offsets; the translator never mentions them. applyText already splices the atom — it also maps every mark on that block through the same splice. Client and server run the same function, so they cannot drift, and a text op stays one op.

That leaves set on from/to for the one case it is actually for: a person deliberately changing what a mark covers.

One ProseMirror mark type per style, each carrying its id

The model's Mark holds an array of styles, which fights ProseMirror's toggleMark. The mapping that works in both directions: declare bold · italic · underline · strike · code · link · colour as separate ProseMirror marks, each with a markId attribute. bodyOf groups runs sharing a markId back into one Mark. Bolding a range that is already italic makes a second Mark with its own id over the same characters, which the model allows and — per its own comment — is exactly what makes two people formatting one paragraph merge instead of collide. 

// procedures/projection.ts — blockNode, today
schema.node("text_block", { blockId, atomId, share }, schema.text(atom.text))

// what it becomes: one text node per run of identical marks
schema.node("text_block", { blockId, atomId, share,
                            variant, level, styleKey, format },
  runsOf(atom.text, block.marks).map(({ text, marks }) =>
    schema.text(text, marks)))
A constraint worth keeping

soleLiteral and drawable stay exactly as they are. Marks are metadata on the block that index into display; they are not atoms. A block is still drawable if and only if its whole content is one literal atom, so images, tables, formulas and prompt blocks continue to travel through the projection untouched rather than being rendered badly.

06The content surface

What it has to start drawing

  • Marks. Bold, italic, underline, strike, code, link, and a colour pair. toDOM on each mark, and CSS in the surface's existing :global(.document-block) block.
  • Variants. A heading has to look like a heading. text_block.toDOM emits h1…h4 · p · blockquote · pre from variant and level, with data-style for the named style.
  • Alignment and spacing. An inline text-align from format.horizontalAlignment, and margins from the resolved style's spaceBefore / spaceAfter.
  • The style set as CSS. One <style> block generated from the document's StyleSet, keyed on data-style, so changing a style repaints every block using it without touching a single node.
  • Comment highlights and the gutter. Section 10.

Nothing is drawn on the page that is not in the document. No margin guide, no ruler, no page-break hint. The panel spec argues for a dashed margin guide precisely because it removes the ruler; we are removing both. A margin is a number in the Layout panel and an area of blank paper, and that is the whole of its presence.

Pagination stops being uniform

layoutMetrics derives 82 characters and 35 lines from one body size of 16px on 26px leading, and linesOfText measures every block against it. That is a number that is only true while every row is the same size. Make one line larger and both figures are wrong for it — which is why they come out of the Layout panel: a characters-per-line readout on a document that has headings is a fact about nothing.

They stay computed, per block. linesOfBlock takes the block's resolved style, works out how many characters of that size fit the measure it has, and converts its leading and its space before and after into the same body-line unit the packer counts in. Change a font size and the block's own budget changes with it. It remains an estimate until pagination measures real line boxes — but an estimate that knows what it is measuring.

The trailing gutter becomes structural

gutterOf returns one number used as symmetric padding, and it collapses to MINIMUM_GUTTER — 0.75rem — before the page gives way. An icon lane does not fit in 0.75rem. Putting comments there means the trailing side reserves a fixed lane and only the leading side goes on collapsing, so the gutter is two numbers rather than one. Small change, worth naming, because it is the difference between the lane being always available and being available on wide screens.

Repaint has to preserve the selection, not just the caret

lay() already re-anchors the caret through anchorAt and positionOf. paint() does not — it builds a fresh state. Changing a margin repaginates and therefore repaints, so paint needs the same treatment, extended from a point to a range so a selection survives a page-setup change.

Where alignment and spacing actually live

Both controls sit in Style, because both are ways the text is set. Where the value is written is the model's business: horizontal and vertical alignment go to BlockFormat on the block, and a named style may carry a default horizontal alignment that the block overrides — TextStyle.horizontalAlignment already exists for exactly that. Spacing is spaceBefore / spaceAfter / lineHeight / indent, which live only on the style; see decision 2.

Leading is baseline to baseline inside a paragraph. There is no letter-spacing field anywhere in the model, and none is proposed — it is a typesetting control almost nobody reaches for and it would need a new field on TextStyle to exist at all.

08Styles

StyleSet is { styles: Record<string, TextStyle>, defaultKey: string } on the body, and TextBlock.style is a key into it — the type comment is explicit that it is "a key into the containing resource's style set, not a copy of its formatting". Today no document has one and nothing reads the field.

A style is a set of formatting with a name. Family, size, weight, line height, space before and after, alignment and indent all live on it. That means the font and size controls in the selection lens are, strictly, controls on the block's style — which is what the panel spec argues for and what the current mock implies without saying.

Styles context panel

  • Actions across the top — New style, Duplicate, Rename — above the search rather than under the list. A panel this narrow puts what you can do where you look first.
  • Then search, then a row per style: name and its typography in shorthand — Heading 1 — IBM Plex Sans 24/32 · 600.
  • Two verbs on the row, both explicit. Selecting it opens the named-style lens beside the panel, which is where every setting is edited. Apply puts the style on the current selection. Selecting a style and applying a style are different intentions and a single click cannot mean both.
  • A document with no StyleSet gets the default set written on first edit, not on open — opening a document should not dirty it.

The default set

Body, Heading 1, Heading 2, Heading 3, Quote, Caption, Code. Seven, matching the six the mock already invented plus a third heading level, because the Sections outline is worth building against more than two levels.

10Comments

The store already has what this needs and nothing reads it. Three threads and five comments are seeded. There is no capabilities/comments/ directory — reads and writes go through the generic store, which is what it is for.

A lane to the right of the page, outside the paper, one row per thread anchored at the vertical position of its anchor's first character. Position comes from EditorView.coordsAtPos on the resolved anchor, recomputed on relayout — the same trigger lay() already fires on.

Writing one

Composing on a selection creates the thread and its first comment together, with quote frozen from the selected text and within from the anchor. Resolution sets resolution rather than deleting — the schema's comment says why, and it is a good reason.

11Sections and Find

Sections

The rail already labels document-editor.navigator as Sections. Headings nested by level, current heading marked, and a filter over the list. It needs exactly one thing that does not exist yet — blocks that know they are headings — which is why it comes after variants.

Each row carries a line and a page, line first. The page is the coarse answer and the line is the precise one, and a heading list is used to get somewhere rather than to know what page something is on. Both are computed and neither is an identifier: the panel spec is right that a page number changes when paper or margins change, and a line number changes for the same reasons and more often. One question this raises and I have not answered: l.14 is the fourteenth line of page 1 here, but a line count from the top of the document is the other reasonable reading. Per-page matches how a filing is cited; whole-document matches how a draft is discussed.

Pages as a second view of the same region are in the panel spec, and breaks and furniture were a third — explicit pageBreak rows plus a way into the header and footer editors. Both are out: page breaks and furniture are not in this round at all, so a section that lists them would list nothing.

Find

A context view rather than a dialog, so it never covers what it is searching. One control at the top switches between Find and Replace; choosing Replace brings a second field and its two buttons — Replace and All — with it, so the panel is never taller than the mode it is in. Below that, the hit count and the hits, each with its line, page and block. Replace goes through ProseMirror so it lands in one undo step and one coalesced change set.

13Four decisions

Each of these changes what gets built, and I would rather ask than assume. My recommendation is on each.

1 · Is “Heading 1” a variant, a style, or both?

TextBlock carries both variant (paragraph · heading · list · quote · code, with a level) and style (a key into the style set). The mock's dropdown lists Body · Heading 1 · Heading 2 · Quote · Caption · Code, which mixes the two vocabularies — Caption is a style with no variant, Heading 1 is a variant with a level.

This matters beyond naming: the Sections outline reads variants, and the Styles panel reads styles. If a heading is only a style, the outline has to hunt for styles named like headings, which is exactly the kind of coupling that rots.

Recommended One dropdown, two fields written together. Picking Heading 1 sets variant: "heading", level: 1 and style: "heading-1". Picking Caption sets variant: "paragraph" and style: "caption". The variant is what the document is; the style is how it looks. The outline reads variants; the styles panel reads styles; the user sees one list.

2 · Does the Spacing section edit the style, or the block?

Spacing has its own section now and sits under Style rather than beside the marks — that part is settled. What is not: the four values it holds (spaceBefore, spaceAfter, lineHeight, indent) exist only on TextStyle. BlockFormat has padding, which is a box property and not the same thing. So typing 12 into After either edits the named style — changing every block that uses it — or needs a new per-block field that does not exist yet.

Recommended It edits the named style, and the section says how many blocks that affects before you touch it. Per-block overrides mean four new fields on BlockFormat and a precedence rule to write down — worth doing if you want it, but as a decision rather than a side effect of putting a number field in a panel.

3 · Multi-selection is non-contiguous corrected

An earlier version of this page recorded this as settled in favour of a selection running across several blocks. That was my recommendation written down as your answer; it was not asked and not agreed. Multi-selection means several disjoint ranges at once.

Which is a larger piece of work than the contiguous reading, and it lands in three places rather than one: ProseMirror needs a custom Selection class and a plugin to draw the ranges; Selection in workspace/tab.ts is { kind, id, at? } — one range — and has to carry a list; and every command in the lens applies once per range instead of once.

A selection that merely spans several blocks stays what it always was: the ordinary case, one range, same lens, mixed controls.

4 · How real are comments in this round?

Reading threads, rendering anchors, highlighting and the gutter are all cheap once the anchors are read. Writing — creating a thread, replying, resolving, mentioning — is a set of writes through the generic store with no capability of its own, which means no validation and no activity rows.

Recommended Read, anchor, highlight and select for real; create, reply and resolve for real through the generic store; mentions and activity deferred. That gives you the interaction you described end to end without a capability that would need designing properly.
