Slide Deck Editor Buildout

Everything the deck editor is today, measured from the code rather than the docs, and everything it has to become to read as professional — across the representation, the client runtime and the editor. Nine decisions have to be settled first; each one below takes your answer in place.

01

Where it stands

The deck's plumbing is finished and its surface is barely started. The runtime is complete and symmetric with the document runtime — buffer, coalesce, rebase, undo, redo, heartbeat, all tested. The change-set path to the store works end to end. What is missing is almost everything above it: the applier accepts six op shapes, one view of fifteen context panels is real, and no inspector exists at all.

1 content view content/deck.svelte — a Konva stage
2 / 15 context Only slides and stage. The other thirteen render the placeholder.
0 / 11 inspector No inspector/ directory. Clicking a shape opens nothing.
6 op shapes Everything else the applier refuses by name.

The one-line summary

Every declared view key already exists in the vocabulary, and the surfaces resolve a key to a file by path. So the whole panel tree is routable and empty: writing inspector/shape.svelte is the entire registration step. The expensive work is not wiring — it is the op vocabulary underneath and the renderer above.

02

The three tiers

A deck exists three times, and the separation is enforced by pnpm lint rather than by convention. Each tier answers a different question, and the boundary between them is what lets the same body be optimistic in the browser and authoritative on the server without either one trusting the other.

Representation

representation/data/types/slide-decks/
representation/data/behavior/slide-decks/

What a deck is. Types plus one pure applier. No Svelte, no network, no browser. Both parties read it: the browser applies an op optimistically and the server applies the same op for real, through the same function.

Frames are fractions of the slide, so a deck survives a change of aspect ratio. One flat id space per deck — an element is found by its own id across every slide.

Client runtime

model/client/slide-deck-runtimes/

What is unsaved. One object per deck, never per tab. A courier: it holds a body, a revision, a buffer of ops and two history stacks, and it does not know what a slide is.

One tick() serves both the edit debounce and the heartbeat, so a re-read can never land on top of an edit in flight. Coalescing folds a whole drag into one op by comparing op path strings — which is why the path grammar is slash-separated.

Editor

What is seen. One content view, the context panels, the inspector lenses, and procedures/ — the only place in the tree that names an op.

A view leaf may import its own category's procedures, the component aliases, $model/client/workspace-state and $capabilities/*. It may not touch the runtime register or $representation, which is why every deck type a view needs is re-exported through procedures/deck.ts.

The break that stops every inspector

Selection is a private let selected = $state<string | undefined>() inside deck.svelte. The inspector surface is driven by view.inspected and view.selection on workspace state, and nothing in the deck editor ever calls view.inspect(…). Clicking a shape draws a Konva transformer and tells no one. The document editor already does this correctly — signalOf(state) reads the ProseMirror selection into a key plus a Selection, and worthSending suppresses the noise. The deck needs the same shape.

A refusal is an answer, not a throw. stale means rebase and retry once; unresolved means an op named something the body does not hold — revert at once.

03

What a deck actually is

This is the whole stored shape, unabridged. Read it against the target state and the holes are obvious: an element has a box and some blocks and nothing that says what kind of thing it is. 

SlideDeckBody = {
  aspectRatio: "16:9" | "4:3"
  theme:  { background?, colors: { text, accent, muted? }, fontFamily? }
  styles: { styles: Record<string, TextStyle>, defaultKey: string }
  layouts:  SlideLayout[]     // key, name, locked[], placeholders[], background?
  slides:   Slide[]
  sections: DeckSection[]     // id, name, firstSlideId — anchored to a slide, not a range
}

Slide = { id, layoutKey?, elements: SlideElement[], notes: ContentBlock[], background?, hidden? }

SlideElement = {
  id: string
  frame: { x, y, width, height }   // fractions 0–1 of the slide
  rotation?: number
  blocks: ContentBlock[]           ← the kind of object is GUESSED from this
  overflow: "clip" | "shrink" | "grow"
  fromPlaceholder?: string
  format?: BlockFormat             ← shared with documents and spreadsheets
}

BlockFormat = { horizontalAlignment?, verticalAlignment?, background?, border?, padding?, valueFormat? }
                     no opacity · no shadow · no cornerRadius · no dash · no cap/join

ContentBlock = TextBlock | FormulaBlock | ImageBlock | TableBlock | PromptBlock
TextBlock  = { id, type, variant, level?, listStyle?, style?, atoms: Atom[], display, marks: Mark[], format? }
Mark       = { id, from, to, style?: MarkStyle[], link?, color? }   // offsets into display, not into atoms

An element has no kind

textOf(element) finds the first text block; if there is one the renderer draws a Konva.Text, otherwise a Konva.Rect. So an empty text box and a rectangle are the same object, an image renders as a blank rectangle, and a table renders as a blank rectangle. One inspector per kind cannot be written honestly on top of a guess.

There is nowhere to put slide paint

Opacity, shadow, corner radius, dash pattern, line cap — none of them exist. The only paint an element carries is BlockFormat, which documents and spreadsheets share. Pushing slide-object vocabulary into the shared content primitive gives the other two editors words they cannot honour.

Already there, and worth knowing

slide-decks/style-set.ts and documents/style-set.ts are the same file twice — TextStyle already carries lineHeight, spaceBefore, spaceAfter, horizontalAlignment and indent in both. So spacing and alignment are not a schema problem on either side. The gap is a renderer that reads them, an inspector that writes them, and an op that carries the write. That is the same three-part gap on both editors, which is exactly why they will stay matched.

notes: ContentBlock[] already sits on every slide, unused. Speaker notes need no schema work at all — only a lens and the text ops that any block edit needs.

Two structural blocks, not twenty-two separate ones

There is no deck target. DeckTarget is slide | element | section | block | atom | mark, so nothing addresses the body's own fields. And set refuses any path deeper than two segments — applySet destructures [id, field, ...rest] and calls refuse when rest is non-empty. So theme/colors/text is unreachable by construction. Both are one-line changes to the type plus a branch in the applier, and both have to land before any theme panel can write.

The good news is that the document's applier is the template for most of this. Its applyText, mapBlock, insertAfter and withoutIds already do the work; the deck's copy differs only in that a block is reached through slide → element → blocks rather than row → blocks.

05

The editor today

What it does nowWhat is wrong with it
Draws the slide with Konva — one stage, one layer, one transformer with resizeEnabled: false and rotateEnabled: false. No resize, no rotate, no text editing. A text element is a single Konva.Text of block.display with no marks, no wrapping control and no alignment. Paint order is array order, so on slide 2 the shapes cover the title.
Renders the slide a second time in the Slides panel, as absolutely positioned divs and spans. Two renderers of one data structure, already drifting: the thumbnail honours format.background and format.border, the canvas honours them only on the blockless branch.
Selects on click, into a local $state. The inspector never hears about it. No shift-click, no marquee, no keyboard selection, no Escape.
Numbered pips along the bottom, one per slide, plus Slide n of m · 16:9 · saved. A second slide selector competing with the Slides panel, and it does not scale past a dozen slides.
Zoom on ctrl + wheel, clamped 50–200%. No visible control, no Fit, no way to discover it.
Slides panel — new, duplicate, delete, drag-reorder, alt+arrow to step. Drag-reorder drops onto a target and marks it with a top border, so the last position is unreachable and the first is awkward. The three action buttons are full-strength blue, teal and red for what are ordinary verbs.
Undo and redo exist on the runtime, with passing tests for invert and coalesce. Nothing calls them. COMMAND_IDS holds four ids — command-bar.open, tab.close, tab.next, tab.previous — and none is undo.

07

Text, shared with documents

Slides hold ContentBlocks, which is what the document editor edits. So the text work is one body of work with two housings, and the two have to stay matched. Here is exactly what the document has, so nothing is copied on trust.

PieceDocument editor todayWhat the deck needs
Editor ProseMirror. Schema is doc › page › blocks_row › text_block › text, and nothing else — marks: {} is literally empty. The same library, a different schema: a slide is not a flow, so there is no page and no row. One instance per text box.
Body ⇄ editor projection.ts. Only a text block whose whole content is one literal atom is drawn; everything else is carried through putBack untouched. The same trick, one level shallower. Copy it.
Editor ⇄ ops translate.ts. Diffs two bodies into ops; the text op is a common-prefix / common-suffix splice. Copy it. The only change is the path: <el>/blocks instead of <row>/blocks.
Selection signal inspecting.ts — signalOf returns one of three: text-selection, empty-block, next-letter. worthSending suppresses caret noise. Copy it, plus a fourth branch: no PM instance focused means an object selection, which is the deck's own concern.
Held selection highlight.ts — a plugin that keeps the range lit on blur, so clicking into the inspector does not appear to deselect. Landed in 7730b78. Copy it verbatim. It is the thing that makes an inspector-driven editor feel right.
next-letter lens Not built The signal fires and the key is declared; no inspector/next-letter.svelte exists, so it renders the placeholder. Build it once, in whichever editor comes first, then copy. It is the text-selection lens with the quote replaced by "what the next keystroke will be".
text-selection lens A mock It reads the quoted text and the character count from the body. Every Style control holds local state and writes nothing; the comments and links are invented rows. Copying it today copies a mock. Making it real needs marks in the schema and a mark op — which is the same work on both sides.
Alignment & spacing Neither Not in the schema, not in the lens, not rendered. Both are already in TextStyle in both editors, and alignment is already in BlockFormat. Add block spacing to BlockFormat once and both get it.

Multi-text selection is one lens, and you were right about that

In the document, a selection that crosses two blocks is the same lens with selection.at set on a different block, and the panel says so in a note. In a deck, with one ProseMirror instance per text box, a selection cannot cross two boxes at all — no editor lets you do that. So "multi-text selection" is either a selection spanning paragraphs inside one box, which is identical, or it does not exist. One lens.

A line is not a box

Every other object is a Frame. A line is two points and it has no meaningful width or height — a diagonal in a bounding box loses which corner it starts at the moment the box is normalised. So a line either carries its own from and to, or it carries a frame plus a diagonal flag, which is the same thing written worse. This is the clearest single argument for giving SlideElement a discriminated content union.

09

Nine decisions

These change what gets built, not how. Each one carries a recommendation; pick an option and the choice is recorded on this page.

D1 What draws a slide?

Konva gives cheap hit-testing and a transformer, and it cannot edit text. Today the slide is already drawn twice — Konva on the stage, DOM in the thumbnail — and the two have started to disagree about which format fields they honour.

D2 Does an element say what it is?

Today the kind is inferred from blocks. An empty text box and a rectangle are indistinguishable, and a line cannot be expressed at all.

D3 Where does slide paint live?

Opacity, shadow, corner radius and a real stroke have no home. BlockFormat is shared with documents and spreadsheets.

D4 How does a multi-selection reach the inspector?

Selection is { kind, id, at? }. It is persisted on the tab and it travels as a WorkspaceOp, so it is undoable. Three objects do not fit.

D5 One ProseMirror per box, or one per slide?

A slide is not a flow, but a single instance would make tabbing between boxes free.

D6 Snapping and guides

You were unsure about both. They are different features and only one of them is cheap.

D7 Where do speaker notes actually live?

There are three candidate homes and the docs describe all three: context/notes, inspector/speaker-notes, and a band on the slide lens. Two writable copies of one paragraph is how one of them quietly wins.

D8 Undo and redo

The runtime's stacks work and are tested. Nothing calls them, and COMMAND_IDS has four members, none of them undo. Meanwhile ProseMirror ships its own history, which the document editor binds to the same chord.

D9 What is in the first cut?

The ledger in §04 is roughly twenty missing op shapes. They do not have to land together, but the renderer decision does gate almost everything visible.

10

The order of work

Assuming the recommendations above. Each stage leaves the editor working — nothing here is a branch that has to land whole.

1

Selection leaves the component

A procedures/selecting.ts in the deck's own tree, modelled on the document's inspecting.ts: turn a canvas gesture into a key plus a Selection, suppress the noise, call view.inspect. Add ids? to Selection. Nothing renders differently; the inspector starts hearing.

app-views/…/slide-deck-editor/procedures/selecting.ts · representation/data/types/workspace/tab.ts · behavior/workspace/invert.ts

2

One renderer

A components/slide-surface/ that draws a body at any scale: DOM boxes, SVG shapes, CSS transform for zoom. The Slides panel's thumbnail and the stage both mount it. Konva leaves deck.svelte; the transform handles, marquee and hit-testing come with the surface.

content/deck.svelte · context/slides.svelte · a new authored component · procedures/stage.ts stays as it is

3

The element gets a kind, and paint

The discriminated content union and ElementPaint, plus the applier branches for insert · remove · move on element and set on rotation, paint, name and overflow. One migration of the two seeded bodies.

representation/data/types/slide-decks/body.ts · op.ts · behavior/slide-decks/apply-ops.ts · seed/slideDeckSnapshots.json

4

Object lenses, reading

slide · shape · line · text-box · image · table · multi-selection. Every value read from the body, every control writing through the ops from stage 3. Align and distribute land here as a pure procedures/arrange.ts with a test per verb.

app-views/…/slide-deck-editor/inspector/*.svelte · procedures/arrange.ts

5

The strip, the rail, and undo

Pips out; Previous, Next, Notes, zoom in. Layers, Insert and Layout panels. edit.undo and edit.redo in COMMAND_IDS, routed to the active tab's runtime. Drag-reorder moves to gap drop zones.

content/deck.svelte · context/layers · insert · layouts · model/client/commands/types.ts

6

Text, both editors together

Marks in the ProseMirror schema and a mark op. Block spacing on BlockFormat. Then the deck's text projection and translate, the held-selection plugin, and the three text lenses — text-selection, next-letter, speaker-notes — built once and copied across.

document-editor/procedures/schema.ts · representation/data/types/content/* · both appliers · both inspector stacks

7

Theme, and the deck target

A deck member on DeckTarget and a set applier that accepts a deeper path. Then the Theme panel, named styles, and the aspect-ratio change with its staged confirmation.

representation/data/types/slide-decks/op.ts · behavior/slide-decks/apply-ops.ts · context/theme.svelte · inspector/theme.svelte · named-style.svelte

Charts, layout editing, Templates and Prompts sit behind all of it. Layout editing in particular is blocked on something structural: RAILS is keyed on the category alone, so the deck has one rail and the three layout-* views have nothing to reach them from.
