01

Where it stands

The plumbing is finished and the surface is barely started. The runtime is complete and symmetric with the document runtime — buffer, coalesce, rebase, undo, redo, heartbeat, all tested — and the change-set path to the store works end to end. Above it: the applier accepts six op shapes, two of fifteen context panels are real, and no inspector exists.

1 content viewcontent/deck.svelte — a Konva stage
2 / 15 contextOnly slides and stage. Thirteen render the placeholder.
0 / 11 inspectorNo inspector/ directory. Clicking a shape opens nothing.
6 op shapesEverything else the applier refuses by name.

The one-line summary

Every declared view key already exists in the vocabulary, and the surfaces resolve a key to a file by path. The whole panel tree is routable and empty: writing inspector/shape.svelte is the entire registration step. The expensive work is the op vocabulary underneath and the renderer above.

02

The three tiers

A deck exists three times, and pnpm lint enforces the separation. Each tier answers a different question, and the boundary between them is what lets the same body be optimistic in the browser and authoritative on the server without either trusting the other.

Representation

representation/data/types/slide-decks/
representation/data/behavior/slide-decks/

What a deck is. Types plus one pure applier. No Svelte, no network, no browser. The browser applies an op optimistically and the server applies the same op for real, through the same function.

Frames are fractions of the slide, so a deck survives a change of aspect ratio. One flat id space per deck — an element is found by its own id across every slide.

Client runtime

model/client/slide-deck-runtimes/

What is unsaved. One object per deck, never per tab. A courier: a body, a revision, a buffer of ops and two history stacks. It does not know what a slide is.

One tick() serves both the edit debounce and the heartbeat, so a re-read can never land on an edit in flight. Coalescing folds a drag into one op by comparing path strings — which is why the path grammar is slash-separated.

The break that stops every inspector

Selection is a private let selected = $state() inside deck.svelte. The inspector is driven by view.inspected and view.selection on workspace state, and nothing in the deck editor ever calls view.inspect(…). Clicking a shape draws a Konva transformer and tells no one. The document editor already does this correctly in procedures/inspecting.ts.

03

The element, redesigned

An element is the visual thing — its frame, rotation, overflow, paint, lock — and it has one content, typed. Not a box: a line has two points, a group has children. This is what is in representation/data/types/slide-decks/body.ts now. 

SlideElement = {
  id: string
  frame: Frame                      // fractions of the slide — or of the group, inside one
  rotation?: number
  overflow?: "clip" | "shrink" | "grow"
  paint?: ElementPaint
  locked?: boolean
  fromPlaceholder?: string
  content: ElementContent           // a has-a, the same way paint is
}

ElementContent =
  | { type: "text";  block: TextBlock }                              // one block; newlines live inside it
  | { type: "shape"; shape: ShapeKind; block?: TextBlock }           // a shape can carry words
  | { type: "line";  from: Point; to: Point; ends?: { start?: LineEnd; end?: LineEnd } }
  | { type: "image"; block: ImageBlock }
  | { type: "table"; block: TableBlock }
  | { type: "chart"; spec: Record<string, unknown> }                // reserved; nothing draws it yet
  | { type: "group"; children: SlideElement[] }

ElementPaint = {
  fill?: string                                          // token or literal; absent is transparent
  stroke?: { color: string; width: number; dash?: "solid" | "dashed" | "dotted" }
  opacity?: number                                       // 0–1, the whole element, text included
  cornerRadius?: number                                  // slide units
  shadow?: { color: string; x: number; y: number; blur: number }
}

ShapeKind = "rectangle" | "ellipse" | "triangle" | "diamond" | "arrow" | "callout"
LineEnd   = "none" | "arrow" | "dot"                                // the arrowhead at either end
SlideLayout gains id, so a layout can be inserted and found like everything else

One TextBlock per text, newlines inside it

Your call, and the simpler one: a text element holds exactly one TextBlock, and a line break is a \n in its display. Marks index the one string as before. Alignment and vertical alignment are styling — block.format.horizontalAlignment and block.format.verticalAlignment, both already on BlockFormat; the box carries no inset of its own. One thing to know: the comment on TextBlock in content-block.ts still says a block holds no newlines. Nothing enforces it; the deck now relies on the opposite. That file was left alone.

There was no group — there is now

A group is an element whose content is other elements. Its frame is in slide fractions and its children's frames are fractions of the group, so moving or resizing the group is one set …/frame op and the children follow. Ungroup rewrites the children back into slide fractions. Grouping is a remove of the members and an insert of the group in one change set, landing where the topmost member was. The applier finds an element by its id at any depth, so a grouped child is addressed like any other.

What it cost

One migration of the two seeded bodies: blocks became content, format became paint. The applier no longer walks known fields — it finds any identified node anywhere in the body, which is what let groups, marks, table rows and cells all arrive at once. Every reader of an element touched the type once.

BlockFormat was left where it is. The deck reads two fields from it — horizontal and vertical alignment — and writes them per block. Font, size, weight, leading and spacing are properties of the named style, and the lenses say so where they edit them. The larger conversation about BlockFormat against TextStyle is still O7.

Every gesture in the target state reduces to an op the applier accepts. The applier was rewritten path-first: the first segment of a path is either one of the body's own fields or an id found anywhere in the deck, and set walks as deep as the path goes, refusing only where a walk stops being useful — into a primitive, or onto a list of identified things, which insert, remove and move own. No deck target, and no depth limit

The body's own fields are addressed by their name at the head of the path — aspectRatio, theme/colors/accent, styles/styles/title/fontSize — so DeckTarget gained nothing, and target became optional on set. A set whose value is null removes the field, which is how rotation goes back to none and a slide's background returns to the theme. Text ops shift the marks they pass through: an insertion before a mark moves it, inside it grows it, at its end extends it; a deletion that swallows a mark drops it.

One more thing the store taught the runtime: a change set that carries the same object instance twice — a group's remove and insert both pointing at one member — is refused as "a cycle". The runtime now flattens every op to plain JSON on apply, which also strips Svelte's state proxies before they cross the wire.

What "100% = fit" changes underneath

view.zoom: null already means "undecided — fill what you are given" on the tab. The strip reads it as 100%; a stored number is a percentage of fit, so drawn = fit × zoom/100. stageMetrics stops multiplying widthRem; the slide has no physical size and the strip stops implying one. The same deck at 100% is a different pixel size on two monitors, which is exactly what fit means.

Drag-reorder in the Slides panel

Drop zones become the gaps — one above the first row, one below the last — and the insertion line is where the slide will land. The op is unchanged: withMovedSlide(body, id, afterId) already takes null for the head. The Slides mock in §07 shows it.

09

The text engine

No ProseMirror on the slide. Text is rendered straight from TextBlock[] and edited in place, and every keystroke becomes an op the runtime already knows how to carry. That is the same three-tier shape as everything else on the deck: the DOM is a projection of the body, never the source.

bodyTextBlock[]atoms · marks · style key · format
renderparagraph → spansStyle key resolves to CSS from TextStyle; marks split display into ranges; a formula atom is a chip showing lastResolvedDisplay
entercontenteditableDouble-click or Enter on a selected box; Escape or a click elsewhere leaves
interceptbeforeinputinsertText → text op · insertParagraph → insert block · deleteContent… → text / remove block · formatBold → mark
selectiongetSelection → (blockId, offset)Collapsed → next-letter; a range → text-selection; held on blur so the inspector can act on it
runtimeapply(ops)Undo is the runtime's; the engine keeps no history of its own
re-renderfrom the bodyCaret restored from (blockId, offset). The DOM never owns state

What it has to do, and nothing more

  • Wrap, align and space paragraphs by CSS — the browser typesets.
  • Overflow: clip clips; shrink measures and steps the font size down; grow lets the box height follow and emits a frame op.
  • Composition (IME) and paste land as one op each; a paste of several lines is one insert block per paragraph.
  • A formula chip is atomic: the caret steps over it, Backspace removes it whole.
  • The same engine draws the speaker notes and every table cell.

What ProseMirror was doing for the document

Caret and selection mapping, IME handling, a schema that refuses bad structure, and a transaction model. The deck's engine takes the first two on directly and gets the third from the applier, which already refuses what it cannot apply. The fourth is the runtime. Whether the document also moves to this engine — so one block type has one text engine — is O6. Either way the lenses and the ops match.

Multi-text selection is one lens, as you said: a range spanning paragraphs inside one box is the same text-selection with at on a different block. A range cannot span two boxes; no editor allows that.

A line is not a box

Every other object is a Frame. A line is two points; a diagonal in a bounding box loses which corner it starts at the moment the box is normalised. That is the clearest single argument for the element union in §03 — and why the line kind carries from and to rather than a frame with a flag.

Settled, and still open

Settled, and now built

  • Every op in §04 is accepted by the applier; all but three are emitted by the editor.
  • The rail is Slides, Templates, Variables, Layers, Layout, Theme, Find, Comments, Prompts. Overview, Stage, Notes, Context and Insert are out.
  • The inspector is Slide, Shape, Line, Text, Image, Table, Group, n objects, Text selection, Next letter, Speaker notes, and a Comments list per object. Theme, named styles and layouts are edited in place in their panels.
  • The strip is Previous · Next · Notes · zoom · Saved. 100% is fit — view.zoom is a percentage of what fits.
  • An element says what it is and has one content; a text element holds one TextBlock with newlines inside; a group holds children in relative frames.
  • Paint is a deck-local ElementPaint on the element. Vertical alignment is styling, on block.format.
  • A multi-selection is the selection carrying ids — ctrl/shift-click or marquee. Group persists it; double-click enters a group.
  • Speaker notes live on the slide and are edited in the notes lens, reached from the strip. The lens does not move between slides.
  • Comments anchor to elements: a badge on the canvas opens a list of that object's threads in the inspector; each row opens the thread.
  • No ProseMirror on the slide. Text is the content-block engine in §09, and it is what runs.
  • Undo, redo and the first cut stayed parked, as you asked.

Of the eight questions, five were answered by building the recommendation; three are still yours.

O1 What draws the slide — and can Konva keep any of it?

Built as recommended

The honest answer to "offload some of it to Konva": a canvas layer cannot sit between two DOM elements. If text boxes are DOM — and they must be, for wrapping, marks and editing — then every Konva shape is either under all the text or over all of it. Konva cannot own an object. It could own the overlay (handles, guides, marquee), but an SVG overlay does that with less code, theme tokens, and no second coordinate system. Charts are already SVG, chosen for exactly those reasons, and their marks carry stable ids — a chart on a slide is selectable down to a bar only if the stage is DOM.

O2 Is a text box one block, or a list of paragraphs?

Settled by you, and built — one TextBlock, newlines inside it. The recommendation below lost; the options stay for the record.

O3 Inside a group, what are the children's frames relative to?

Built as recommended

O4 With no Insert panel and no toolbar, how does an object get onto a slide?

Still open — the one thing the build cannot do

You turned down Add in Layers, and Insert left the rail. newElement() and the insert op are ready; nothing calls them. Pick a home and it is an afternoon.

O5 Snapping and guides

Built as recommended — Alt suspends; guides are named while a drag matches.

O6 Does the document editor move to the same text engine?

Still open

The deck's engine exists now and edits the same TextBlock the document holds. The document still runs ProseMirror with an empty mark schema.

O7 What does the deck read from BlockFormat while the bigger conversation waits?

Built as recommended, plus vertical alignment — two fields read and written per block, as you moved vertical alignment into styling. The bigger conversation is still yours.

O8 100% is fit — confirm

Confirmed by you, and built — the same deck at 100% is a different pixel size on two monitors, which is the point.
