The slide deck editor, end to end

A Konva canvas, a client runtime that buffers what you did, and a pair of remote procedures that move a deck body between the browser and a JSON-file store. This is what each part owns, where the boundaries are enforced, and what a dragged shape actually travels through.

Boundaries

Five trees, and what may reach what

The deck is not one folder. It is spread across five trees on purpose, and the separation is enforced by pnpm lint rather than by convention — 65 structural checks, of which four shape this feature directly.

The rule with teeth. runtime-through-workspace-state matches /\b(attach|acquire|createRuntime)\s*\(/ against the raw text of every view leaf — markup and comments included. No view file may contain the characters attach( anywhere, which is why the accessor on workspace state is named slideDeckRuntime.

The editor

What the canvas owns

deck.svelte takes no props. It reads view.active.resourceId for which deck, and holds a working copy of the body that moves the instant you drag — the runtime is told afterwards.

ConcernWhere it livesWhy there
Geometry procedures/stage.ts A slide is a ratio, not a size. Its coordinate space is 1280×720 units for 16:9, 960×720 for 4:3 — the height is declared, the width follows the ratio.
Element frames stage.ts · toPixels / toFrame Frames are fractions of the slide, 0–1, so a deck survives a change of aspect ratio. Conversion happens in exactly one place.
Zoom TabView.zoom Per-tab workspace state, not deck state. Two tabs on one deck keep their own, and a zoom is an undoable WorkspaceOp.
Colour procedures/tokens.ts Canvas cannot read CSS variables, and a theme value may be light-dark(…) — valid CSS, invalid fillStyle. A hidden probe element resolves each token through the browser.
Ops procedures/deck.ts withElementFrame returns { body, ops } together, so the next body and the op describing it cannot disagree.
Zoom is a stage transform, not a redraw. Nodes are placed in slide units and never move when you zoom; stage.scale() and stage.size() carry it. The slide box and the canvas take the same rounded pixel number from one derivation, so they cannot drift apart by a frame — measured at 0.00px divergence across 118 frames of a zoom gesture, down from 19.08px when the canvas was sized by observing the box.

The runtime

One object per deck, never per tab

SlideDeckRuntime is a courier. It holds the last body the server served, the ops you have made since, and the revision those ops were authored against. It does not know what a slide is.

MemberTypeMeaning
bodySlideDeckBody?The last body the leader served. undefined until the first read lands.
revisionnumberWhat the buffered ops are stated against.
syncSyncStateloading · saving · saved · rebasing · error
pendingnumberOps in the buffer, unsent.
apply(ops)voidRecord one gesture: push to the undo stack, buffer, schedule.
tick()PromiseSend what it holds, or read what it does not.
Coalescing folds a drag into one op. Repeated sets on one path fold into the earliest, keeping the last value and the first was. Relatedness is decided on the strings — equal, or one continuing the other at a / boundary — because the runtime resolves no paths. That is why the op path grammar is slash-separated: el-4/frame.

Integration

How a view reaches a runtime

A view cannot import the register, so workspace state routes to it. The register is a borrowed dependency, handed in at construction and never returned in the client graph.

The round trip

What a dragged shape travels through

client server — — network boundary

  1. Drag ends. toFrame converts the node's position from slide units to a fraction. withElementFrame returns the next body and one set op.

  2. The working copy moves immediately. Nothing waits for the server — this is the optimistic apply. runtime.apply([op]) buffers the op and arms the debounce.

  3. Two seconds later, or at fifty ops, tick() finds a non-empty buffer and flushes. coalesce folds a whole drag into one op.

  4. The change set crosses once. submitSlideDeckChanges is the only outbound call, carrying baseRevision so the server can tell whether it was stated against what it holds.

  5. The server rebuilds the body. applyOps finds the element by id across every slide — a deck has one flat id space — and replaces its frame. Nothing partial is written.

  6. Two rows land together: a slideDeckChangeSets row for the audit, and the slideDeckSnapshots leader advanced by one revision.

  7. The runtime adopts the new revision, then syncs. The next heartbeat that finds an empty buffer re-reads the leader and the canvas redraws.

Refusal

What happens when the server says no

A refusal is an answer, not a throw — an exception would be indistinguishable from a network failure, which needs the opposite handling.

ReasonMeansResponse
stale Authored against a revision the leader has moved past. Rebase onto the server's revision, re-state the ops, retry once. If that fails, revert.
unresolved An op names something the body does not hold — a deleted element, an unknown field. Revert at once. Re-sending would be asking the same question twice.

Reverting drops the change set, re-reads the body, and leaves the runtime at saved. It is a reader again afterwards, not a casualty: there is nothing left for anyone to review.

Not built

What the shape anticipates and does not yet do

  • Only one op is applicable. applyOps handles set on element/frame and refuses everything else by name, so an op the editor learns to emit before the server learns to apply it fails where it was sent.
  • Undo and redo exist and are unbound. The stacks work and are tested; nothing in the UI calls them.
  • No resize, rotate, text editing, or slide insertion. The Transformer runs with resizeEnabled: false and rotateEnabled: false.
  • No print model. handout was removed from the body: printing is an arrangement of N slides on a sheet, which a page setup has nowhere to hold.
  • A canvas is opaque to a screen reader. Elements are reachable by pointer only; a Layers panel is the intended answer.
