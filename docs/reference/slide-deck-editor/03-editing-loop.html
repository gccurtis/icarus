03 · the loop

From a gesture to the store

Four worked examples — a drag, a keystroke, a lens control and a comment — each followed from the pointer to the row it ends up in, and back to the screens that change because of it.

Content view content/deck.svelte Renderer components/authored/slide-surface/ Runtime model/client/slide-deck-runtimes/ Capability capabilities/slide-deck/
1

Dragging a shape

  1. Pointer down on the canvas. slide-surface.svelte · pointerDown finds the element under the pointer through its data-item attribute, resolves it to the top-level object (topLevel: a grouped child stands for its group unless the child itself is already selected), and calls onselect([id]) if it was not selected. It records a press gesture and captures the pointer on the stage.
  2. Select. deck.svelte · select looks the ids up in the body, asks procedures/selecting.ts · elementsSignal which lens fits — one shape → slide-deck-editor.shape, several → multi-selection — and calls view.inspect(key, { kind: "elements", id, ids }). The inspector loads inspector/shape.svelte; the canvas draws the outline because its selected prop is derived from view.selection.
  3. Pointer move past three units turns the press into a move: the surface keeps a draft frame per moved object, asks snap (a callback into procedures/snapping.ts) for the nearest sibling edge, and draws guides. Nothing has been written.
  4. Pointer up calls onframes([{ id, frame }], true) once. deck.svelte · frames runs withElementFrame(body, id, frame) for each, which converts an absolute frame back to a group-relative one where needed and returns { op: "set", path: "el-3/frame", value, was }.
  5. Apply. runtime.apply(ops) deep-copies the ops through JSON (a Svelte state proxy or a shared object instance would otherwise reach the store and be refused as “a cycle”), applies them to the live body, appends them to the buffer and pushes one undo entry. The body changed, so the canvas, the Layers panel and the Slides thumbnail re-render.
  6. Flush. Two seconds later (or after fifty ops) the buffer is coalesced — repeated sets on one path fold into one with the last value and the first was — and sent as { resourceId, baseRevision, ops, touched }.
  7. Server. submitSlideDeckChanges gates on the scope, validates the change set, refuses a stale base revision, runs the same applyOps, writes a slideDeckChangeSets row and updates the leader slideDeckSnapshots row and the deck's updatedAt. The answer carries the new revision; the runtime records it and reads the leader back.
2

Typing into a shape

  1. With the shape selected and nothing being edited, a printable key reaches deck.svelte · keydown (a window listener that ignores keys aimed at inputs and anything a popover has already handled). It calls startTyping(element, key).
  2. A shape with no text gets one: withSet(body, "el-3/content/block", emptyText(defaultKey, key)). A shape with text gets the key appended: replaced(block, length, length, key) from procedures/typing.ts, which is a text op on the last literal atom.
  3. editing is set to the block id and view.inspect("slide-deck-editor.next-letter", { kind: "next-letter", id: "blk-9@1" }) puts the caret's lens up. The content view's selected keeps the shape in it while editing, so the outline stays.
  4. slide-surface-text.svelte sees editing turn true, focuses its contenteditable, and places the caret at the end. From here every keystroke is a beforeinput it intercepts: insertText, insertParagraph (a \n), the deletions, paste, cut — each becomes onedit({ blockId, from, to, insert }) and the browser's own edit is prevented. deck.svelte · edited turns that into ops with replaced.
  5. The caret is reported on every selection change (oncaret), and deck.svelte · caret keeps the workspace selection in step — next-letter for a collapsed caret, text-selection for a range — without re-inspecting when nothing changed.
  6. Escape, or a click on the shape outside its text, calls onexit; deck.svelte · exit clears editing and re-selects the holder, so the shape lens comes back.

Why a text box grows

The item renderer watches the text element with a ResizeObserver when the element's overflow is grow. When the text's height differs from the frame's by more than a pixel it reports ongrow(id, height) on the next animation frame, and deck.svelte · grow writes the frame's height. It is suppressed while a gesture is in progress so a resize drag is not fought mid-way.

3

A lens control: the font size of one shape's text

  1. The next-letter lens renders components/text-style.svelte with the block id. The component reads the runtime itself: the block, its holder (holderOf), the named style, the block's format.
  2. Typing 40 into Size fires PanelNumber's onchange once, on Enter or blur. The component calls set("blk-9/format/fontSize", 40).
  3. withSet compares against the current value and returns nothing if it is unchanged; otherwise one set op, with was: null because the block had no format. The applier creates the missing format object on the way down.
  4. The scene re-derives; textSceneOf now reads the block's 40 before the style's 20; only that shape's text changes. The Style panel's Size, which edits styles/styles/body/fontSize, is the one that changes every box wearing the style.

Every lens control follows this pattern: derive from the runtime, write one withSet or withSets, never hold a copy. The one exception is the text-style component's FG colour on a range, which becomes a mark (colouredMark) rather than a block field.

4

A comment on a shape

  1. The shape lens's Comment action (components/comment-action.svelte) inspects slide-deck-editor.threads with { kind: "threads", id: "el-3" }. The threads lens lists that object's threads and holds a composer.
  2. Posting calls the comments capability: startThread({ target: { kind: "slides", id: deckId }, within: { kind: "element", elementId }, text }). On the server the author and the project come from the request's scope — a client cannot post as someone else — and two rows are created, a commentThreads row and its first comments row.
  3. The lens then calls refresh() on its read({ path: "commentThreads" }) and read({ path: "comments" }) queries. Because every reader of those tables holds its query for its whole life (see 08 · queries), the refresh reaches the canvas — which draws the badge and the dashed outline — and the Comments panel at once.
  4. Opening the thread inspects general.comment with { kind: "comment", id: threadId }: the comment lens shows the state, the author, the text as a quote, Reply / Resolve, the anchor row (which opens the slide and the object's threads), the replies and a composer. Reply and resolve are the other two procedures of the same capability.
5

How the panels see the same body

Every panel and lens opens with the same six lines: read workspaceState(), derive the deck id from view.active.resourceId, attach the runtime for it in an effect, derive body from runtime.body. Nothing is passed in. When the canvas moves a shape, the Layers panel re-orders because it derives its rows from placedOn(slide); the Slides thumbnail redraws because it calls sceneOf(body, slide) in its template; the inspector's Geometry re-reads the frame because ElementGeometry derives it from the body. The runtime is the bus.

The one thing a panel keeps locally is a draft that is not yet a fact: the text of a comment being written, the name of a layout about to be saved, which insert kind is armed for placing. The last of those is the only state two views share, and it is a module-level $state in procedures/placing.svelte.ts because the Insert panel arms it and the canvas consumes it.
