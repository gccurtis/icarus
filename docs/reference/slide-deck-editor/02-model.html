02 · representation

The deck model and the applier

One body type, five op kinds, one pure function that applies them. The body is what the store holds and what the runtime shows; the ops are what crosses the wire; the applier is the same code in the browser and on the server, which is why an edit the browser accepted is one the server will accept too.

1

The body

SlideDeckBody = {
  aspectRatio: `${number}:${number}`     // "16:9", "4:3", "21:9" — any two whole numbers
  theme: { background?, colors: { text, accent, muted? }, fontFamily? }
  styles: { defaultKey, styles: Record<key, TextStyle> }   // the named styles
  layouts: SlideLayout[]
  slides: Slide[]
  sections: DeckSection[]                // read but never edited; the editor ignores them
}

Slide = { id, layoutKey?, elements: SlideElement[], notes: ContentBlock[], background?, hidden? }

SlideLayout = { id, key, name, locked: SlideElement[], placeholders: SlidePlaceholder[], background? }

Frames are fractions of the slide — { x: 0.08, y: 0.34, width: 0.5, height: 0.4 } — so a deck whose ratio changes keeps every object where it was. The only place pixels exist is the renderer, which multiplies by the stage's units (720 high, width from the ratio) and scales the whole stage with one CSS transform.

2

The element: what it is, and what it has

SlideElement = {
  id, frame, rotation?,
  overflow?: "clip" | "shrink" | "grow",   // what a text box does when its text does not fit
  paint?: ElementPaint,                     // how it is drawn — fill, border, opacity, corner, shadow
  locked?, fromPlaceholder?,
  content: ElementContent                   // what it is
}

ElementContent =
  | { type: "text";  block: TextBlock }                                   // one block; newlines inside it
  | { type: "shape"; shape: ShapeKind; block?: TextBlock }                // text is optional and centred
  | { type: "line";  from: Point; to: Point; ends?: { start?, end? } }
  | { type: "image"; block: ImageBlock }
  | { type: "table"; block: TableBlock; rowHeights?: number[] }
  | { type: "chart"; spec }                                               // reserved
  | { type: "group"; children: SlideElement[] }                          // children in fractions of the group

ElementPaint = {
  fill?: string                                  // a --token or a hex
  stroke?: { color, width, dash? }               // the panels call this the border
  opacity?: number                               // 0–1; absent is 1
  cornerRadius?: number
  shadow?: { color, x, y, blur }                 // the panels show it as a direction and an intensity
}

An element says what it is and has one content. The type discriminates everything downstream: which lens opens, what the renderer draws, what the Layers panel calls it. Nothing on a slide carries a name; a shape is “Shape” and a text box is its first line.

A group holds its children with frames relative to its own, so moving a group is one set on one frame. Grouping is a remove of the members and an insert of the group in one change set; the group lands where the topmost member was. Ungrouping rewrites the children back to slide fractions.

A text box is one TextBlock and a line break is a \n in its display. Its default overflow is grow: its frame's height follows its text, in both directions.

3

Text: three layers of style

Where a run of text gets its look from, innermost winning:

  1. The named style — body.styles.styles[block.style ?? defaultKey], a TextStyle: font family, size, weight, colour, line height, space before and after, horizontal and vertical alignment. Shared by every block that wears it; edited in the Style panel.
  2. The block's own format — block.format, a BlockFormat: the same fields as overrides, plus background, border and padding. Edited by the Text section of a lens; it is what makes one shape's text 40px while every other shape stays at 20.
  3. Marks on a range — block.marks: bold, italic, underline, strikethrough, code, and a colour. Edited from a text selection.
BlockFormat = {
  horizontalAlignment?, verticalAlignment?,
  fontFamily?, fontSize?, color?, lineHeight?, spaceBefore?, spaceAfter?,   // added on this branch
  background?, border?: { color, width, style }, padding?, valueFormat?
}

procedures/scene.ts is the one place the three are merged (textSceneOf): it reads the block's field, then the style's, then a default, and hands the renderer a flat TextScene. A shape's text is centred by default in both axes, a text box's is top-left.

4

Tables: a grid derived from rows

A TableBlock is rows of cells; a cell may span. The grid position of every cell is derived, never stored: procedures/tables.ts · gridOf walks the rows, skips the squares already covered by a span, and gives each cell its row, column and spans. Everything else — the renderer's grid-row / grid-column, the rectangle test for merging, which cell a column-insert lands after — reads that grid.

  • Merge requires the picked cells to tile a rectangle exactly. The first-picked cell is kept — its blocks and format — and re-inserted at the rectangle's top-left with the rectangle's spans; the others are removed.
  • Split clears the spans and inserts blank cells into each row the span covered, at the right column.
  • Column widths are on the block (columnWidths, one number per column, used as fr units); row heights are on the element's content (rowHeights), because a document table flows and a slide table does not.
  • Per-cell fill and border are the cell's format.background and format.border; a cell's text alignment is its text block's format.
  • headerRows is still on the block and the renderer still shades those rows; no control edits it any more.
5

Layouts

A layout is a locked copy of a slide: Save slide as layout in the Style panel copies every element on the slide (fresh ids) into layout.locked, with the slide's background. A slide made from that layout (New ▾ in the Slides panel) has layoutKey set and no elements of its own; the renderer draws the layout's locked elements underneath the slide's, marked fixed so they cannot be hovered, selected or moved. The seeded layouts still carry placeholders, which a new slide turns into empty text boxes; nothing edits a layout in place yet.

6

The five ops

{ op: "set",    path, value, was, target? }                     // any field; null removes it
{ op: "insert", path, ids, after, values, target }             // into any identified list
{ op: "remove", path, ids, after, values, target }
{ op: "move",   path, id, after, wasAfter, target }
{ op: "text",   path, at, insert, remove, target: "atom" }      // splice a literal atom; marks shift

Every op carries what it undid — was, values, wasAfter, remove — so every op inverts, which is what the runtime's history needs and why an insert names its ids.

Paths

A path is segments joined by /. The first segment is either one of the body's root fields (aspectRatio theme styles slides sections layouts) or any id found anywhere in the deck — a slide, an element, a block, a cell, a row, a mark, a layout. The applier finds the node by id and walks the rest of the path from there: 

el-3/frame                      set the frame of element el-3, wherever it is (even inside a group)
el-3/paint/stroke/color         set deep; missing intermediate objects are created
blk-9/format/fontSize           a block's own font size
styles/styles/body/color        the named style
slide-2/elements                the list an insert / remove / move of an element acts on
el-g1/content/children          the list inside a group
blk-t/rows · row-1/cells        table rows, and one row's cells
blk-9/marks · blk-9/atoms       a block's marks, and the atoms a text op splices

What the applier refuses

  • A set onto a list of identified things — slide-2/elements, blk-t/rows — because that list is what insert, remove and move own. A list of plain numbers such as columnWidths is fine to set.
  • A set that would walk through a primitive.
  • An insert or move whose after is not in the list, and a remove of an id that is not there.
  • A text op whose remove does not match what is at at.

A refusal throws inside applyOps. In the browser that means the gesture fails where it was made and nothing reaches the buffer; on the server it means the change set is answered unresolved and the runtime re-reads the leader body.

7

Ids

The client mints ids — procedures/ids.ts · mint("slide" | "element" | "block" | "atom" | "layout") — because a new slide has to be selected the moment it is asked for, before any round trip. The suffix is random rather than sequential because two clients editing one deck mint against the same base revision. The id space is flat: a slide, an element and a cell are all found by nodeIn(body, id).
