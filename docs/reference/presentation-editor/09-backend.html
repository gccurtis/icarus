09 · capabilities and the store

The back end

The server side of the editor uses the presentation, template, comment, and store capabilities. The comment capability is new; the slide and template read boundaries now reconcile older represented bodies with the editor's explicit element model. No table or store schema was added or changed.

Capabilities capabilities/{presentation,templates,store,comments}/ Server model serverModel().store via $runtime/server/start.server Scope requireScope() from $runtime/server/scope.server
1

What a capability is, mechanically

A directory under capabilities/ with index.remote.ts that exports SvelteKit remote functions — query(…) for reads, command(…) for writes — each wrapping a procedure at api/<name>/<name>.ts. A procedure's first line is await requireScope() (who is asking, in which project) and its second is a validator from api/<name>/validate-<name>.ts that throws on anything it cannot act on. It then reaches the store only through serverModel().store — read(path), create(table, fields), update(path, value), remove(path) — and returns a typed result from types/. A <name>.md says what the capability is for; unit tests under test/unit mock the server model and the scope.

On the client a remote query returns a handle with current, ready and refresh(); a command returns a promise. Nothing invalidates a query when a command runs, so the caller refreshes what it changed (page 08 § 7).

2

presentation and template boundaries

readPresentationBody
A query. Finds the leader row in presentationSnapshots for the project and presentation (role: "leader"), normalizes a pre-editor body if needed, and returns { revision, body }, or null. The runtime refreshes it on every sync.
submitPresentationChanges
A command taking { changeSet: { resourceId, baseRevision, ops, touched } }. Validates the shape (at least one op, each with an op kind and a path). Refuses unresolved if no leader exists; stale if baseRevision is not the leader's revision; unresolved with the applier's message if applyOps throws. Otherwise it creates a presentationChangeSets row (revision, base revision, tier “recent”, ops, touched, actor, time), replaces the leader snapshot's body and revision, stamps presentations.<id>.updatedAt / updatedBy, and answers { accepted: true, revision }.
applyOps
The capability's api/submit-presentation-changes/apply-ops.ts is a one-line wrapper over the representation's applier that prefixes the error. It is the same function the browser ran, which is the whole guarantee that an optimistic edit and an accepted one agree.
templates/bodyOf
Slide templates pass through the same pure normalizer, then the template capability validates the canonical content union, paint, nested groups, layouts, references, and ids. Instantiation therefore writes a body the editor can open.

The existing protocol did not change. Its shared leader boundary and the template validator did; the applier and its unit test were also rewritten for the new element shape. Page 10 § 3 records why normalization was needed.

3

store, used as it was

read({ path }) answers a whole table as { kind: "table", rows } or a field as { kind: "field", value }, gated on scope. The editor reads five things through it: commentThreads, comments and users (the Comments panel, the threads lens, the comment lens, the Comment action and the canvas badges), presentations.<id>.title (the title bar) and the resource title a comment is anchored to. The editor never writes through store; presentation writes go through the change set and comment writes through the comments capability.

4

comments, new

Three commands. Reading is deliberately not here — threads and comments are rows, read through store like any table — so the capability only adds to them.

ProcedureInputValidationEffectResult
startThread{ target, within?, quote?, text }target.kind ∈ document · slides · spreadsheet with an id; within one of slide { slideId }, element { elementId }, cell { rowId, columnId }, text { blockId, from, to }; text non-empty after trimmingCreates a commentThreads row (project from scope, target, within, quote, createdBy from scope, updatedAt) and its first comments row (one paragraph block, no mentions, author from scope){ threadId, commentId }
reply{ threadId, text }both present; text non-emptyFinds the thread in the asking project (else throws “no thread”); creates a comments row; bumps the thread's updatedAt{ commentId }
resolveThread{ threadId, resolved }id present; resolved booleantrue sets resolution: { by, at }; false removes it; either bumps updatedAt{ resolved }

Who is speaking is never a parameter. The author and the project come from the scope; a caller cannot file a remark as someone else or into a project it cannot open. A thread in another project is not found rather than refused.

What it took to make it pass the structural lint:

  • api/shared/thread.ts looks a thread up by reading the whole commentThreads table through the store model and filtering by id and project. It returns a structural ThreadRow type of its own rather than importing the table's row type from $representation/store; the first version did that import and storage-through-a-model refused it.
  • api/shared/paragraph.ts builds the one-paragraph TextBlock a comment holds, minting ids with crypto.randomUUID because the server has no access to the editor's mint.
  • Ids are converted with asId from the representation's core behaviour, as the presentation capability does.
  • index.remote.ts declares exactly the three procedures and re-exports their input and result types; the entry files are named for their directories; each procedure's first two statements are the scope and the validator.
  • The unit test hoists a fake server model (tables as maps, a log of updates and removals) and a fake scope, then imports the procedures, so it covers the project check and the trim without a store.
