08 · the client model

The runtime

Two client-side models sit between the views and the server. The presentation runtime holds the live body and everything not yet saved. The workspace state holds what is open, focused, selected and inspected. This branch changed one line of the first and nothing in the second, but leans on rules of both that are worth writing down.

1

The register, and one runtime per open presentation

createPresentationRuntimes(configuration) is called once by the client runtime at start and reads its thresholds and stage settings from configuration — it refuses to build without them. It keeps two maps: open and settling. attach(id) returns the open runtime if there is one (and pokes a sync), revives a settling one, or creates one and subscribes it; release(id) moves it to settling, flushes what it holds, and forgets it once the flush lands unless it ended in error or needs review. releaseAll runs when the client instance closes.

The views never touch the register. workspaceState().presentationRuntime(presentationId) calls attach; it is idempotent, so every panel, lens and section attaching the same presentation gets the same object, and a second tab on one presentation costs nothing. 

class Runtime {
  body: PresentationBody | undefined   // $state — what is shown
  revision: number                  // the leader revision the body is at
  sync: SyncState                   // loading · saved · saving · rebasing · needs-review · offline · error
  buffer: PresentationOp[]             // applied here, not yet sent
  undoStack / redoStack             // gestures, each a list of ops
  inFlight: boolean
  stage: StageSettings              // unitsHigh, zoom bounds and step, gutter bounds
}
2

apply, buffer, schedule

runtime.apply(ops) is the only way a view changes a presentation. It applies the ops to the live body first — an op the applier refuses throws here, at the gesture, and never reaches the buffer — then appends them to the buffer, pushes them as one undo entry, clears redo, and schedules a flush. One apply is one undoable gesture however many ops it carries, which is why a drag of five objects or a merge of six cells is a single call.

Scheduling: if the buffer has reached flushAfterOps (50) it flushes now; otherwise a timer of flushAfterMs (2 s) is reset from the last op. A heartbeat every syncEveryMs wakes the runtime to tick: send what it holds, or read what it does not.

3

flush: coalesce, submit, rebase, revert

  1. Coalesce. A run of sets on one path folds into one with the last value and the first was — a 300-event drag becomes one op with a correct inverse — unless an op on the same or related ground (a prefix either way, compared by segment) sits between them. Inserts, removes, moves and text ops never fold.
  2. Submit { resourceId, baseRevision, ops, touched } through submitPresentationChanges. Two concurrent flushes join the same promise.
  3. Accepted → record the revision, mark saved (or saving if more arrived meanwhile), and sync.
  4. Stale (someone else advanced the leader) → rebase: adopt the server's revision, put the refused ops back at the front of the buffer, mark rebasing, and resubmit once. A second refusal reverts.
  5. Unresolved (the server's applier threw) → revert: drop the buffer and re-read the leader, so the screen shows what the store holds.
  6. A thrown request (network) → the ops go back in front of the buffer and the state is error; the next tick tries again.

sync only runs when the runtime is settled — an empty buffer and nothing in flight — because only a reader may take the leader's word. It calls refresh() on the readPresentationBody query rather than awaiting it, since the query would otherwise answer from the client cache with the body the page loaded with.

4

Undo and redo

History is not the buffer. undo pops the last gesture, pushes it to redo, inverts its ops in reverse order (set swaps value and was; insert ↔ remove; move swaps after and wasAfter; text swaps the two strings) and buffers the inverse like any edit. Undo survives a flush. Every op the editor makes therefore has to carry an honest was, which is why withSet reads the current value before writing and why a remove carries the removed values.

5

What changed on this branch

One line in Runtime.apply: the ops are deep-copied through JSON before being applied and buffered.

Why. The views build ops from values they read out of runtime.body, which is a Svelte $state proxy. An op whose value or values was such an object — a frame copied by spread, a whole element in an insert, a removed row in a remove — carried a live proxy: it kept tracking the body after it was buffered, and the request serialiser refused it. Copying at the boundary means the buffer owns plain data, the change set that leaves is what was applied, and an undo entry is what it was when recorded. Nothing else in the runtime, its methods or its tests changed.

6

The workspace state, as the editor uses it

workspaceState() is one $state object per client. Every change to it is a WorkspaceOp performed through perform: applied, logged for undo, and buffered for persistence with the same after-ops / after-ms shape the presentation uses. The presentation editor calls five of its methods:

MethodOpUsed for
open({ category, resourceId, focus })land on the existing tabShowing a slide: the Slides panel, Previous / Next, Find, a comment's anchor.
inspect(key, selection)inspectEvery selection. Throws if the key is not a declared lens.
clear()inspect → emptyOnly when there is no slide to fall back to.
setZoom(n)zoomThe strip and the pinch.
presentationRuntime(id)—Attaching the presentation.

The one type this branch touched is Selection, which gained an optional ids so a multi-selection and a cell selection can be carried, persisted and restored like any other selection. The shared inspect() canonicalizer must copy that optional list along with kind, id, and at; dropping it collapses every multi-selection to its primary id. Regression tests prove both immediate workspace state and the submitted operation retain every member. The workspace does not interpret the ids; only the presentation's selecting.ts reads them.

Because the selection is workspace state, it is persisted and restored with the tab. A restored tab can therefore open on a stale lens — a cell of a table that no longer exists — and every lens guards for its subject being absent by showing its empty state instead of throwing.

7

The query-lifetime rule

The store's read({ path }) is a SvelteKit remote query. The object it returns is a tracked handle: it subscribes while it is alive and is released when nothing references it. A handle created inside a $derived is recreated on every re-evaluation, and the previous one is released — which is how the comment badges and the Comments panel came to stop updating after a post: the handle that had been refreshed was not the handle anyone was still reading.

The rule every view on this branch follows:

const threadRows = read({ path: "commentThreads" });   // once, at component init
const threads = $derived(rowsOf(threadRows).filter(...)); // derive from the held handle
await startThread(...);
await Promise.all([threadRows.refresh(), commentRows.refresh()]); // refresh the same handle

A command does not invalidate queries on its own, so every procedure call in the editor is followed by a refresh() of the handles it affected. Two queries are still created inside a derived — the presentation title in the content view and the resource title in the comment lens; both are read-only and keyed on an id, so they are recreated only when that id changes and nothing ever refreshes them.
