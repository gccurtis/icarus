01 · the shape of the thing

How the system works

A presentation is a JSON body. The client holds one live copy of it per open presentation and every edit is a small operation on that copy; the same operation is sent to the server, which applies it to the canonical copy. Everything the person sees — the slide, the panels, the inspector — is a projection of the live body and of one piece of workspace state that says what is selected.

The one place a representation type is allowed to surface in the editor is procedures/presentation.ts, which re-exports the types the views need. That is a lint rule, not a convention: a .svelte file under app-views that imports $representation fails the build's structural lint, and so does one whose props are anything other than ids, primitives and callbacks. A view is told which thing to show and reads the thing itself from the runtime.

2

The file system is the registry

There is no map from a panel's name to its component anywhere. A context view key presentation-editor.layers is the file app-views/categories/presentation-editor/context/layers.svelte; an inspector key presentation-editor.cell is inspector/cell.svelte; a general lens general.comment is app-views/general/comment/comment.svelte. The context surface and the inspector surface each hold one import.meta.glob over those directories and load the file the key names.

Three lists say which keys exist and where they appear, and all three are checked at compile time:

  • representation/data/types/workspace/views.ts — the union of every context and inspector key. A key that is not here cannot be inspected: view.inspect throws.
  • representation/data/behavior/workspace/views.ts — the same list as a runtime set, which isInspectorView reads.
  • representation/data/behavior/workspace/opening.ts — per category, the rail: which context views are offered and in what order, and which one a fresh tab opens on. The presentation's rail is Slides · Insert · Layers · Style · Find · Comments · Templates · Variables · Prompts.

The rail's labels and icons are the fourth list, surfaces/context/procedures/rail-entries.ts, typed as a Record over every context view so a key with no label does not compile.

3

The five surfaces, and the one state they all read

The frame is a tab strip, a context panel with a rail, the centre, the inspector and a status strip. None of them talks to another. Each reads workspaceState() — one $state object per client — and writes back through its methods. For the presentation editor the fields that matter are:

active.category / resourceId
Which category the tab is, and which presentation.
active.focus
The slide being looked at. Set by view.open({ focus }); the Slides panel, Previous/Next and Find all set it.
context
The context view showing on the rail.
inspected
The lens key the inspector is showing, or "empty".
selection
{ kind, id, at?, ids? } — what the lens is about. Kinds the presentation uses: slide, elements (with ids), cells (id is the table, ids the cells), notes, threads, text-selection and next-letter (id is blockId@offset, at the other end), comment.
zoom
Per cent of the fitted size; null means fit. 100 is fit.
frame
The two flank widths and whether each is collapsed.

Selection lives in the workspace, not in the editor. Clicking a shape on the canvas calls view.inspect("presentation-editor.shape", { kind: "elements", id, ids: [id] }); the canvas then draws its outline by reading view.selection back, and the Layers panel highlights the same row for the same reason. There is no local selected-ids state anywhere; the one piece of local state the content view keeps is editing, the block whose text currently has a caret, and even that is mirrored into the workspace as a text-selection so the inspector can show the caret's lens.

The renderer is an authored component rather than part of the editor because the Slides panel and the Style panel draw thumbnails with the same component the centre uses. It takes a SurfaceScene — plain data built by procedures/scene.ts — so it never sees a body or an op.

6

Constraints that shaped every file

  • Views take ids and callbacks. view-takes-ids-and-callbacks fails any .svelte prop under app-views that is not a primitive, an id or a function. So ElementGeometry takes elementId, not an element; TextStyle takes blockId.
  • A capability is a directory with a shape. index.remote.ts declares only procedures; every api/<name>/ holds <name>.ts; each entry calls requireScope() first and a validator second; nothing under capabilities imports a view or reaches into $representation/store.
  • Authored components are named for their directory and imported at the library's index; the panel vocabulary lives in components/authored/panel/ and a lens never draws its own button.
  • Colour literals are not written in source. Everything is a --token-* custom property; a user's chosen colour is the one exception and is stored as data.
  • The registry is the tree. Adding a lens is adding a file and a key; adding a rail entry is adding a key, a label and a line in opening.ts.
