03 · the crossing

The capabilities

Twelve procedures on templates, four on the new resource-sets, and one exclusion in project-resources. Each one opens with the scope gate, validates before it reads, and answers a refusal as a value. This page says what every one does and what it refuses.

1

The shape every procedure keeps

export const commitTemplateStage = async (input: unknown) => {
  const scope = await requireScope();
  const asked = validateCommitTemplateStage(input);
  const store = serverModel().store;
  …
};

The gate first, the input second, the one server object at its index, then reads, refusals as values, then writes. Validators live beside their procedure and are named for it; shared checks live in api/shared/validation.ts. Refusals are { accepted: false, reason, detail } with a closed reason union per procedure, so a panel switches on the reason and shows the detail. Stored rows are re-admitted before projection or mutation; a malformed row is quarantined rather than crashing the list.

The remote index wraps commands so that the queries a command changes are refreshed in the same request: the library after anything that changes it, the template detail after anything that changes one template, the resource's stage record and the workspace's table read after a stage opens or closes. A panel names those same queries in .updates(), which is how the new state lands in the client cache along with the command's result.

2

Visibility: a template is the project's

visibleTemplate and the library filter by projectId === scope.projectId where main filtered by owner. Everything follows from that: the library is the project's, a template in another project answers not-found everywhere, and anyone the scope admits to the project may edit, save into, duplicate and delete a template, so the owner-only forbidden refusal is gone from update, remove and save. userId and createdBy record who made a template and grant nothing; every item reports availability: "project". Creation, duplication and a save from a resource stamp the scope's project on the row, and admission refuses a stored row without one.

4

templates: the stage lifecycle

openTemplateStage({ templateId })

Finds the template's stage and returns it with reused: true; otherwise creates a scratch documents or slideDecks row titled Template · <name>, a revision-zero leader snapshot holding the template body with its resource tag removed, and the stage row. Refuses not-found for an invisible template and unsupported-body for a corrupt one or a spreadsheet.

commitTemplateStage({ stageId, baseRevision })

The stage must be in this project (not-found otherwise); the template must still be in it (not-found); the template's revision must equal baseRevision (stale), which, since the stage is the only writer of the body, means only that another session's save landed first. The scratch resource's leader body is read, made portable, tagged with the stage's target, and admitted with bodyOf. Variables the body names that the template does not declare are declared with the name as their label. The template's body, variables and revision are written, a version row follows, and the stage's templateRevision moves to the new revision. The answer carries what portability dropped.

discardTemplateStage({ stageId })

Removes, in order, the comments on threads targeting the scratch resource, those threads, the resource's change sets, its snapshots, the resource row, and last the stage row, so a failure midway leaves a stage that still names what remains rather than rows nothing can find. Anyone in the project may discard, because the stage is the project's.

What updateTemplate and removeTemplate now do

An update never touches the body, so it carries the template's stage to the revision it makes: a rename in the inspector or a variable declared in the editor does not make the next save a conflict. Delete discards the template's stage and version rows along with it and touches no resource, because none refers back to it; main's detach-and-refuse over provenance is gone with the provenance.

A thread cannot be started on a stage resource. startThread in the comments capability reads the stage table, as a subject capability reads a table it does not own, and refuses with "a template's working copy takes no comments"; the deck's comment panels replace their composer with the same sentence.

5

templates: making and using

createTemplateFromResource({ target, resourceId, name, description?, tags?, slideId? })

Reads the resource's leader body in this project; with a slideId, takes the deck of that one slide with deckOfSlide; makes it portable; admits it; declares the variable names the body uses; writes the template at revision one with a version row. The source resource is not touched and never learns a template was made from it. The validator refuses a document id for a deck target and vice versa, and a slideId on a document.

updateTemplate with patch.variables

The patch may now replace the whole variable list, validated by the same variablesOf that admits stored rows (unique names, labels, defaults naming declared variables). If the body still names a variable the new list drops, the update refuses with variable-in-use and the names. The one-description patch survives unchanged.

instantiateTemplate with answers?

Answers are the caller's, a resource set per variable name, or nothing; the Insert modal is what collects them. A named set an answer points at is checked to exist here before anything is written; scopes are resolved through the answers, then each variable's default, which may itself name a set, then the whole project. A body naming a variable the template does not declare refuses with unsupported-body and the names, rather than guessing. The resource it makes carries no reference to the template; the template's lastUsedAt is set instead, and that is what the library's recency reads. The inspector's Use collects answers through the same modal Insert shows.

The catalogue a count is resolved over is documents, decks, spreadsheets, findings and research threads in the project, minus any resource a stage occupies. Kinds are the same five words Project Overview draws. A set's own validation mirrors the templates capability's term rules with the two project-bound terms added, and shares nothing with it, because a capability is entered at its index and nothing else.

7

project-resources

readProjectResourceIndex reads the stage rows for the project first and skips any resource whose id one occupies, so a scratch copy never appears in Project Overview's table, in New Tab's recents, or in a comment's resource picker. Nothing else about the index changed.

8

Boundaries kept, and one not yet

  • Nothing reaches inside a capability. The panels import both indexes and nothing below them; the templates capability reaches resource-sets nowhere. It reads the resourceSets table through the store when an answer names a set, which is what a subject capability does with a table it does not own.
  • Nothing under capabilities/ holds state or imports a view. The eleven capability checks and the four across-tree checks are clean.
  • Every stored row is re-admitted. A stage row that names a resource in the wrong table and a set whose rule is not two lists are invisible rather than fatal.
  • Not a transaction across tables. Opening a stage writes three tables; discarding one writes up to six. The store is failure-safe per table, and each write order is chosen so a partial failure leaves rows that are still reachable, but a represented transaction remains the same known gap the capability document already names.
