01 · the system

How templates work now

One vocabulary, two capabilities, and four places a person touches templates: the library, the document editor, the deck editor, and Project Overview. This page follows a template through its life and names the file responsible at each step.

Vocabulary representation/data/types/templates/template.ts Crossing capabilities/templates/index.remote.ts · capabilities/resource-sets/index.remote.ts Panels app-views/categories/*/context/*.svelte
1

What a template is

A templates row in one project: a name, tags, a portable body, and a list of variables. Portable means the body names nothing that only exists as a live resource: no formula ids, no derived-output ids, no links to people or resources, no stored images, no scope terms naming a set or a resource. That was already the contract; what is new is that a body can be made portable from a live one rather than only admitted or refused. The contract holds inside one project as much as across two, because a template turns a value into a function: a formula keeps its expression and loses its instance, and a prompt's scope is what the variables fill.

A body is a document, a deck, or a spreadsheet, exactly as before. A template saved from one slide is a deck template holding that slide, the layout it uses, and the theme and styles it is drawn with, and no sections, because a section is a place in a deck and a lone slide is not in one. Nothing marks it afterwards; it is a deck like any other.

A variable is a hole a prompt's scope can name: { select: "variable", name }. It carries a label, a description, and a default: the whole project, particular kinds, or one of the project's named sets. A variable declared without a default means the whole project, so a template always resolves. When a template is inserted, the person is asked what each variable should select here, with the default offered first; an answer wins over the default for that one use and is stored nowhere.

A template's life

MadecreateTemplate · createTemplateFromResourceEmpty of a kind, or from a live document, a live deck, or one slide, body made portable, in the project the person is in
OpenedopenTemplateStageA scratch resource holds the body; a stage row names the template and the revision it was taken from; the editor tab opens on its Templates panel
Editeddocument-editor · slide-deck-editorThe ordinary editor, runtime and change sets work on the scratch resource unchanged; variables and their defaults are set in the panel
SavedcommitTemplateStageThe scratch leader body, made portable and validated, becomes the template's next revision
UsedinstantiateTemplate · insertA new resource, or rows and slides inserted into an open one, each variable answered in a modal or left to its default
DiscardeddiscardTemplateStageThe stage row and scratch resource go, with the resource's snapshots, change sets and comments

Three facts hold the shape together. A template belongs to one project, so its library, its stage and everyone who may edit it are that project's. A stage is one per template, shared by everyone in the project, so opening again resumes the same copy, two people editing a template collaborate through the editor as they would on any document, and the copy is the only thing that ever writes the template's body: a copy and its template cannot drift apart. And no resource refers back to a template: a copy made by Use or Insert is its own from the first moment, later changes to the template never reach it, and the template records its own last use. A stage resource is not made from a template either; it is the template while it is open, so editing is never a use.

3

Where the browser meets the server

Every read and write about a template goes through capabilities/templates/index.remote.ts, and every one about a set through capabilities/resource-sets/index.remote.ts. Each procedure opens with requireScope(), validates its input before reading the store, answers refusals as ordinary accepted: false values, and re-admits every stored row before trusting it. The remote wrappers refresh the queries a command changes, the library, the template's detail, the resource's stage record, so a panel that named those queries in .updates() sees the new state without a second round trip.

Nothing template-shaped crosses through the generic store capability; that is the rule its own document states. The editors do read a resource's title through the workspace's scoped table read, so opening or discarding a stage refreshes that read as well, and the editor tab is named the moment it opens rather than after a second fetch.

4

How the editors take part without changing

The content surfaces, document.svelte and deck.svelte, are untouched. They read view.active.resourceId, attach the runtime for it through workspace state, and draw whatever body the runtime holds. A stage resource is an ordinary documents or slideDecks row with an ordinary leader snapshot, so the editor cannot tell the difference and does not need to. The tab is named from the row's title, which the stage sets to Template · <name>, so the strip says what is open.

What knows the difference is the Templates context panel. It asks readResourceTemplate({ resourceId }) and gets back the stage it is (if any) and the template it was made from (if any). A stage changes the panel's verbs and adds two bands; an ordinary resource gets the save form instead. Both share the template list.

Inserting a template into what is open is an edit like any other: the panel builds ops with a procedure and calls runtime.apply(ops), so undo, flush, rebase and the change-set ledger all apply. Saving a stage flushes the runtime first and refuses while anything is still pending or failed, because the capability reads the leader snapshot and a buffered keystroke would otherwise be left out of the template.

A working copy takes no comments. The comments capability refuses to start a thread on a stage resource, and the deck's comment panels say so in place of the composer, because a comment is one more thing that does not travel with a template.

A tab can now be opened straight onto a named context view: Target.context, honoured when the category's rail offers it. Saving a resource as a template uses it to land on the new template's Templates panel, so Save to template and Discard are where the person's hand already is.

5

Resource sets

A set is include minus exclude, each a list of terms: the whole project, a list of kinds matched by segment, named resources, or another set by id. The resourceSets table existed and was seeded; the capability over it is new. Reading the project's sets resolves each one against the documents, decks, spreadsheets, findings and research threads the project holds and reports the count, never stored, so the number beside a set's name cannot go stale. A stage resource is left out of that catalogue.

In Project Overview the Contexts panel makes, renames, describes, changes and deletes sets, and says when one matches nothing. A prompt's scope can name a set, and so can a template variable's default, because the template is the project's; deleting a set is refused while another set or a template default still names it.

6

What the prompt block will pick from

Prompt blocks choosing a variable are a later feature. The model is ready for it: a prompt's scope already holds { select: "variable", name } terms; the variable's default says what the template means by it; the Insert modal is where a person overrides it; and resolveTemplateScopes turns all of that into a plain resource set at instantiation or insertion. The panel's variable list is the picker's source.
