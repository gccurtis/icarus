02 · representation

The model

One new table, one new field, one new term and five pure functions. No new type, no new body kind: a slide saved on its own is a deck template that happens to hold one slide, and a variable carries one default and nothing else. Everything here compiles to a declaration or runs the same on either side of the boundary, which is the whole standard for this tree.

A slide is a deck template

export type TemplateBody =
  | ({ resource: "document" } & DocumentBody)
  | ({ resource: "slides" } & SlideDeckBody)
  | ({ resource: "spreadsheet" } & SpreadsheetTemplate);

Exactly as on main. Saving one slide asks the capability for a deck template with a slideId; deckOfSlide(deck, slideId) is the one function that makes the body: the named slide, the layout its layoutKey names, the theme and the styles, and no sections, because a section is a place in a deck and a lone slide is not in one. After that nothing distinguishes it from a deck template someone built with one slide, which is the point: everything that draws, validates, stages and inserts a deck already works on it, and a template of three slides needs nothing new either.

A variable and its default

export type TemplateVariable = {
  name: string;
  label: string;
  description?: string;
  default?: TemplatedResourceSet;
};

export type TemplatedTerm =
  | ProjectTerm
  | KindsTerm
  | NamedSetTerm
  | { select: "variable"; name: string };

The variable is exactly as on main. The default is a templated resource set, and its term vocabulary gained one member: a set term naming one of the project's sets, which is sound now that a template belongs to a project and can never land in another. A default may therefore say the whole project, particular kinds, one of the project's sets, or another variable. Two readings changed with it: an absent default means the whole project, so every variable always resolves to something; and answers are what the Insert modal collects, one resource set per variable, which win over the default for that one use and are stored nowhere.

A named set a default points at cannot be deleted while the template names it; the resource-sets capability refuses with in-use and says which template.

Templates and stages

export type TemplateFields = {
  projectId: Id<"projects">;
  userId: Id<"users">;
  …
  lastUsedAt?: number;
};

export type TemplateStageFields = {
  projectId: Id<"projects">;
  templateId: Id<"templates">;
  templateRevision: number;
  target: Exclude<TemplateBody["resource"], "spreadsheet">;
  resourceId: string;
  createdBy: Actor;
  updatedAt: number;
};

projectId and lastUsedAt are the two fields this work adds to a table main already had: a template belongs to the project it was made in, records its own last use, and userId stays as a record of who made it, granting nothing. One field it removes: main's templateId on documents, decks and spreadsheets, because a resource made from a template is a copy and knows nothing of where it came from. templateStages is the one table it adds. The scratch resource is an ordinary documents or slideDecks row with a revision-zero leader snapshot; the stage row is what makes it a stage. There is one per template and it belongs to nobody in particular: two people editing a template edit the same copy through the editor's own collaboration, so no row says who is editing. templateRevision is the revision the copy corresponds to: the one it was taken from, saved to, or carried to by an edit that left the body alone. Since the stage is the only thing that writes the template's body, it equals the template's revision at every rest. A spreadsheet cannot be staged until its editor lands, and the type says so.

4

resolveTemplateScopes

Moved out of the capability's bodies.ts, because the editors need it at insert time and a view may not reach inside a capability. It walks a body and, for every prompt's scope, replaces each variable term:

  • a caller's answer for the name splices its include terms in (an answer that excludes is refused, for the same reason a default that excludes always was: a difference does not flatten into two lists);
  • else the variable's default is expanded recursively with a memo and a cycle guard, its excludes crossing to the opposite side; a set term passes through as itself;
  • else, for a declared variable with no default or one that reaches itself, the whole project;
  • a name the template does not declare keeps its term and is reported in undeclared, and instantiation refuses on it rather than guessing.

A 10,000-term guard survives from the original. variableNamesIn(body) lists the names a body refers to; it is what stops a variable being removed while the body still names it, and what declares names a saved body uses.

5

portableBodyOf

A live body, stripped of what a template body may not carry, with each removal said back as a sentence. The list mirrors assertPortableBody in the capability, which refuses the same things: formula ids on atoms, blocks and function values; derived-output ids on prompts; actor, persona and resource links on marks; file and storage image sources; image backgrounds; ranges into other spreadsheets; references to resources; and set or resources terms in prompt scopes. What survives is exactly what admission accepts, which is what lets a save or a commit succeed rather than refuse.

The sentences, such as "Dropped 2 links to things in the project.", are returned by the capability and shown in the panel, so a person never saves less than they had without being told. The list holds inside one project as much as across two, because a template turns a value into a function. A formula atom keeps its expression and loses its formulaId; that is its project-neutral form, and the document editor draws it with a dashed outline until a formula is made for it again. Images stored in the project are the one item likely to change: a later change may store them with the template so they travel.

6

withFreshIds

A fragment with every identified thing renamed, so it can be inserted beside content that may already hold the originals. Ids are found by where they sit: rows, blocks, atoms, marks, slides, elements, children, layouts, sections, cells, a caption or a block. The caller supplies the minting function, keyed by that hint, because each editor spells its ids its own way (#b… in a document, el-… in a deck) and behavior may not read randomness. Mark ends and section anchors follow the ids they name; a reference to an id the fragment does not carry is left alone.

7

resolveResourceSet

Which of a project's resources a set selects right now, given a catalogue of references and a map of named sets for following set terms. Kinds match by segment through the existing kindMatches, so externalFile names every subkind under it. A set that reaches itself contributes nothing on the second visit. The capability builds the catalogue from five tables and leaves stage resources out; this function knows nothing about tables.

Tests on this page
