Panels and flows

Three context panels were built and two views changed. None of them draws anything the panel vocabulary and the overlay vocabulary do not already ship, none imports another view, and each computes through a procedure module that is tested without a browser.

1

How a panel is wired

The context surface loads the file whose path is the active key, so document-editor.templates is categories/document-editor/context/templates.svelte and the file replaced the eight-line placeholder that held the key. Every panel opens the same way as its neighbours: 

const view = workspaceState();
const documentId = $derived(view.active.resourceId);
let runtime = $state<DocumentRuntime | undefined>(undefined);
$effect(() => { runtime = documentId === undefined ? undefined : view.documentRuntime(documentId); });
const body = $derived(runtime?.body);

const library = templateLibrary();
const sets = resourceSets();
const resourceQuery = $derived(resourceTemplate(documentId));
const stage = $derived(stageIn(resourceQuery?.current));
const template = $derived(detailIn(templateDetail(stage?.templateId)?.current));

Four queries decide what the panel is: the library (what can be inserted or edited), the project's sets (what a default or an answer may name), the resource's template record (is this a stage, what was it made from), and, for a stage, the template's detail (its variables). Writes go through runtime.apply(ops) for the body and through the procedure module's remote wrappers for everything else; each wrapper runs under view.singleFlight keyed on what it does, so a double click cannot send two saves. The panel is gated on the resource id rather than on the body, so a runtime attaching to a new tab does not unmount the bands for a frame.

2

The document editor's Templates panel

An ordinary document. A name field and Save. Save is disabled until there is a name; pressing it copies the document into a new template, made portable, and opens that template for editing in a new tab, landed on its Templates panel, where the save says what it dropped.

A staged copy. Save to template and Discard in the header, both disabled while the runtime has unsaved work. An Editing template band names the template and its revision.

Variables (stage only): a field and Add declare a variable from a label, the name minted as lower_snake and made unique. Each variable is a collapsed section holding its description first, then its default as a sentence on a button. The button opens a modal, built from the overlay vocabulary, with one switch for everything in the project, one per kind, and one per named set the project holds; confirming writes the whole variable list through updateTemplate at the revision the panel read. Remove sits last. A refusal, a stale revision or a variable the body still names, comes back as a banner.

The templates. Below either state, every document template behind one search field. A row wraps its name, says its variable count and revision, and carries Insert and Edit. No kinds, no icons: in a document editor every one of them is a document.

3

Insert

Pressing Insert on a template with variables opens one modal, Insert “name”, with a row per variable: its label, its description, and a select whose first option is Default · the default read as a sentence, followed by everything in the project, one option per kind, and one per named set. Confirming turns the choices into answers, one resource set per variable that was not left at its default, and inserts. A template with no variables inserts at once. This is the ask the review described: each variable, its default shown, one modal for all of them.

insertionOf(body, template, afterRowId, mode, answers) in the document procedures builds the ops: one insert of rows after the row holding the caret (or at the end), with every id minted afresh, preceded by an insert of each named style the document lacks. In resolve mode the template's prompt scopes are resolved through the answers, then the defaults. In keep mode, when the open document is itself a stage, nothing is asked: scopes are left as variable terms and the inserted template's variables are merged into the stage's template, because a template inserted into a template should bring its holes with it.

The deck's insertionOf does the same for slides: layouts whose key the deck lacks are inserted, styles the deck lacks are set, and the slides are inserted after the current one, with the deck's own version of a shared layout key winning (fork 2). The first inserted row or slide is shown. What lands is a copy: later changes to the template do not reach it, and it can be undone like any edit.

4

The slide-deck editor's Templates panel

The same panel with one difference: under the name field sit Save deck and Save slide. Save deck copies the whole deck; Save slide copies the current slide, the one the tab is focused on, into a deck template holding that slide alone. Both open the new template for editing in a new tab. The list holds every deck template, one-slide ones included, because there is no second kind.

The stage lifecycle, from the panel's side

Workthe editor, unchangedTyping, layout, styles, comments, slides, all against the scratch resource
SaveSave to templateawait runtime.flush(); refuse if anything is pending or failed; commitTemplateStage at the template's current revision; say what was dropped
DiscardDiscard, after a confirmflush, discardTemplateStage, then close the tab

Save uses the template's current revision, read from the template detail the panel already holds, as its base. Edits that leave the body alone, a rename in the inspector or a variable declared in this panel, carry the stage's revision forward with them, and the stage is the only thing that writes the body, so the base is stale only when a second session's save landed first; that session's panel re-reads and saves again. Saving keeps the stage open, so saving twice is ordinary.

Discard closes the tab only after the capability has removed the resource, so a runtime sync that lands afterwards reads nothing and draws an empty body rather than resurrecting the row. Comments cannot be made on the copy: the deck's comment panels say so where the composer would be, and the capability refuses one that arrives anyway.

6

The library, the editor door, and the inspector

Library. Double-clicking a row or a recent card opens the template's copy in its editor, landed on the Templates panel, through editTemplate in the procedures; a spreadsheet says why it cannot. Every template is the project's, so every row says Project and nobody is marked as editing.

The editor door. templates.editor stays a content view because stored workspaces name it. It now opens the focused template's copy and lands the singleton back on the library; if the open is refused it says why under the return bar.

Inspector. Four actions in one row: Use, Edit, Duplicate, Delete. Each variable's disclosure shows its description, then a Default row whose button reads the rule as a sentence and opens the same modal the editors use, named sets included. Declaring and removing variables stay in the editor's panel, beside the body that names them. Use asks the same way Insert does: one modal listing each variable with its default first, then Create; instantiating a template on its own is still instantiating it.

7

Project Overview's Contexts panel

The rail already offered project-overview.contexts; the file is new. New set in the actions row opens a name field (blank makes "New set N") and the rule toggles, the whole project, five kinds to include, five to exclude, with the rule read back as a sentence while it is built. The list is filterable; each set is a collapsed section titled with its name and its live count ("3 resources", or "matches nothing" with a gap note), holding an editable name and description, the rule as a sentence, the count, the creator, the toggles, and Delete. Every write is compare-and-swap at the revision the panel read; a refusal is a banner, including the refusal to delete a set a template default still names.

8

Rules the panels keep

  • No panel imports another view or a surface. Each reaches its own category's procedures, the two capability indexes, the panel and overlay vocabularies, and workspace state. The modals are the overlay vocabulary's OverlayModal, repeated in the views that need them, because a view may not be shared across categories.
  • No panel attaches a runtime. view.documentRuntime(id) and view.slideDeckRuntime(id) are the one attachment, so the panel and the canvas share one edit buffer.
  • Every disabled control says why in its title; every write that can be refused draws the refusal.
  • The two editor panels are copies, not a shared component, which is the rule for a view two categories both need. Their procedure modules differ where the editors differ: the document inserts rows after the caret's row; the deck inserts slides after the focused slide and merges layouts.
