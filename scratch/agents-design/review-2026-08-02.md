# Agents design — review

**Date:** 2026-08-02
**Reviewed:** the seven files in `scratch/agents-design/`, against `apps/backend/src` as of
commit `e06a8f5`, the per-module `docs/` packages, and `docs/claude-notes/`.
**Method:** full read of the design, full read of Persona, Document's application and store
layers, the job runtime, the composition root, and the resource-lifecycle helpers.

---

## Verdict

The design is good. Its five load-bearing ideas — four frozen inputs, the consumed-prefix
rule, commit-before-dispatch, dual recording, and deny-by-default policy — are each the
right answer, and each is expressed in the vocabulary the runtime already uses rather than
inventing a parallel framework. Nothing in the core model needs to be thrown away.

What it needs is three different kinds of work, and they should not be confused with each
other:

| Class | What it is | Count | Needs you? |
| --- | --- | --- | --- |
| **A · Stale facts** | The design was written 2026-08-01. A lot shipped on 2026-08-02. | 6 | No — mechanical |
| **B · Convention misfits** | Names, file layout, error ladder, barrel, tests | 9 | No — mechanical |
| **C · Soundness and open decisions** | Things that are wrong, missing, or genuinely undecided | 12 | **Yes** |

Class C is what the rest of this document is for. Nine of the twelve are cheap to settle
now and expensive after the build starts.

**The single most important finding** is C7: the requirement the design places on every
mutating target — `lookup(requestDigest)` — is both **unsatisfied by any capability in the
tree** and **unnecessary**. Removing it deletes the design's only outbound requirement on
other capabilities and collapses its most awkward recovery branch. Read that one first.

### What fits, and fits well

| Serial commands, concurrent queries | Every capability | Correct |

### C1 · `maxReadToolRoundsPerStep` describes graceful bounding that does not exist

**Severity: real bug in the plan.**

`execution.md` sets `maxReadToolRoundsPerStep: 6` and passes it to `reasonWithTools`, and
`failure and retry` classifies bound exhaustion as `bounded` — "settles the run rather than
hanging".

But `Intelligence.reasonWithToolsInternal` ends:

```ts
throw new Error(`Reasoning tool loop exceeded max rounds (${maxRounds})`);
```

It **throws**, and it throws a bare `Error` with no structured decision, no partial result,
and no usage accounting returned. So a read-heavy reason step does not settle as `bounded`
with a summary — it explodes, and the runner cannot tell "the model burned its read budget"
apart from "the provider failed".

Derived Outputs lives with this because its tool loop is one shot inside one refresh. Agents
cannot: a step that exhausts reads is a *normal* event that must produce a `system` message
telling the model to decide with what it has.

**Options.**

- **(a) Catch and reclassify.** The runner catches the throw, appends a `system` message
  ("read budget exhausted, decide now"), and retries the reason step once with reads
  disabled. Zero platform change. Loses the usage figures from the aborted loop.
- **(b) Add a non-throwing variant to Intelligence.** `reasonWithToolsStructured` gains a
  `onBoundExceeded: "throw" | "return"` option, returning `{ structured: undefined, usage,
  rounds, exhausted: true }`. ~15 lines in `0-platform/intelligence`, and it makes the loop
  honest for every future caller.

**Recommend (b).** Losing usage accounting matters when `maxTokensPerTask` is a budget the
task enforces. But (a) is a legitimate v1 if you want zero platform churn — just say so in
the design rather than implying bounding works today.

### C2 · Task creation holds the global serial slot for an unbounded scope resolution

**Severity: real, and easy to miss.**

The serial queue has **exactly one active slot for the whole backend**. Every Document
command, General File upload, Connector delete, Persona write, and Template registration
shares it.

`execution.md` puts `knowledge.resolveScope(...)` inside `task.create`, on the serial queue.
`Knowledge.resolveScope` with an empty scope does:

```ts
(await this.store.listSources()).map(...)                       // every source in the project
...
await Promise.all(resolvedSourceIds.map(id => resolver.describeSource(id)))   // N lookups
```

An empty scope means "the whole project", which is the design's own default
(`contextEntries: [] → whole project`). So the *default* task creation walks the entire
Knowledge source list and issues one resource lookup per source — while holding the lock
that every other mutation in the backend is queued behind.

Nothing else on the serial queue does unbounded work. Document's serial commands are
bounded by one aggregate; Persona's are two small reads and a CAS.

**Options.**

- **(a) Split creation into two jobs.** `agents.task.prepare` (concurrent) resolves persona
  and scope and stashes them; `agents.task.commit` (serial) writes. Costs a durable
  intermediate row and a second idempotency surface.
- **(b) Freeze the scope at first-run start, not at creation.** The run's first step
  resolves and pins the manifest onto the task, concurrently. Still before any model call,
  so the freeze guarantee survives; but "frozen at creation" becomes "frozen at first run",
  and a task created now and started in an hour sees the later corpus.
- **(c) Accept it, and document the bound.** Add `maxScopeSources` to `AgentLimits` and
  reject creation above it, so at least the serial hold is bounded.
- **(d) Resolve concurrently *before* the command job.** Not expressible — transport hands
  the whole request to one job.

**Recommend (b) with a caveat, or (c) if you want the simplest thing.** (b) is honest —
"frozen before the first model call" is the guarantee that actually matters, and it is the
one Persona's consumer laws state ("persist before calling"). (a) is the most correct and
the most machinery.

### C3 · Recovery has no home in the runtime

`execution.md` says "Startup and a periodic sweep reconcile durable state against the empty
queue." The tree has exactly three recurring/recovery mechanisms and this is none of them:

| Mechanism | Where | Shape |
| --- | --- | --- |
| Startup recovery | `startBackend.ts`, awaited **before** `app.listen` | `document.recoverPendingAttempts()`, `*.publishPendingActivity()` |
| `ConnectorSyncScheduler` | `1-init/create/`, started **after** `app.listen` | Timers that enqueue normal Jobs |
| `ResourceRetentionScheduler` | `0-utils/persistence/`, started after `app.listen` | Process-level storage maintenance over bound ports |

A fourth recurring sweeper is a new mechanism, and the codebase's stated non-goal is "no
second orchestration framework".

Also note `file-architecture.md` says "Recovery starts after the HTTP listener binds, for
the same reason the connector sync scheduler does." That is the wrong precedent: Document's
attempt recovery runs **before** `listen`, awaited, so no request can race a half-recovered
attempt. Connector's rule is about *timers*, not recovery.

**Options.**

- **(a) Startup-only, awaited before `listen`.** Exactly Document. Anything stuck between
  restarts stays stuck until the next restart.
- **(b) Startup + opportunistic.** Startup as above, plus: whenever a run settles, sweep that
  task's siblings. Covers the common case (a lost dispatch) without a timer.
- **(c) Startup + a periodic `agents.task.recover` dispatched by a timer in `1-init`.**
  Matches Connector; a genuinely new recurring mechanism for the tree.

**Recommend (b).** It is strictly more than Document does, costs no new mechanism, and (c)
can be added later if a real stuck-task rate shows up in `agents.recover` logs.

### C4 · There is no cancellation primitive, and the design should say so

`JobDefinition` has no `AbortSignal`. `Intelligence` methods accept `signal` but every
caller passes `undefined` (`knowledge/embedder.ts` carries the comment: *"AbortSignal is
undefined for now — wire it through when request-level cancellation is added"*).

The design's "cancel takes effect at the next step boundary" is therefore **correct**, but
it reads as a design choice when it is currently the only option. Worth stating plainly, and
worth noting that a long reason step means cancel latency is one model call — which for a
user clicking "stop" is the number they will complain about.

No decision needed; a doc correction.

## 2 · Data model

### C5 · Tasks sit outside the resource lifecycle contract

**Severity: the largest structural question in the design.**

As of 2026-08-02 every user-facing persisted resource follows one contract (general-updates
#13): typed current table, capability history table, update archives *N* and writes *N+1*,
logical delete archives *N* and appends a terminal deletion at *N+1*, purge is the only
irreversible removal, and the capability is bound into `ResourceRetentionScheduler` via
`bindResourceRetentionPort(name, capability)` with `pruneHistory` / `purgeExpired`.

Ten capabilities are bound in `startBackend.ts`. Agents, as designed, would be the eleventh
persisted capability and the **first not bound at all** — no history, no delete, no purge,
no retention (`store.md`: "Tasks, exchange, tool calls: kept indefinitely"; D23: "there is
deliberately no task-delete command").

There *is* precedent for exclusion: Activity is append-only and explicitly excluded from
retention, as are transaction outboxes, receipts, and claims. The question is which of those
two families a task belongs to.

The argument for ledger (as designed): a task is the only Agents-side evidence of calls that
were proposed, refused, and denied. Deleting it destroys the audit trail that justifies
letting an agent act at all.

The argument against: `agents.db` then grows monotonically forever, holding `request_json`
for every proposal (the full arguments, by design) and every exchange message. Activity rows
are small and uniform; agent tasks are not. And a user who creates a task by mistake has no
way to remove it.

**Options.**

- **(a) Full resource lifecycle.** `task.delete` + `task.purge`, history table, retention
  binding. Consistent with everything else; contradicts D23's audit argument.
- **(b) Ledger, but present in the sweep.** No delete command. Bind into the retention
  scheduler anyway, where `pruneHistory` prunes **transcripts** for settled tasks past the
  cutoff (including failed ones, which the design currently keeps forever with no sweep at
  all) and `purgeExpired` is a no-op. The capability appears in the retention roster; the
  audit record survives.
- **(c) As designed.** Cite the Activity precedent explicitly in the docs so it reads as a
  decision rather than an omission.

**Recommend (b).** It is the smallest change that stops the one genuinely unbounded thing
(failed-task transcripts, which hold provider-facing message arrays and never get pruned
under the current design) and it puts Agents on the retention roster where an operator
expects to find it. (a) is defensible if you want tasks deletable; it should be a deliberate
answer to D23, not a default.

### C6 · Three separate naming conflicts with the tree

**`origin`.** The design uses `"operator" | "automation"`, plus a fourth author vocabulary
`"operator" | "agent" | "automation" | "system"`. The tree has:

| Vocabulary | Used by |
| --- | --- |
| `user \| agent \| automation \| system` | Activity, Comments, Templates |
| `interactive \| agent \| automation` | Document (its adapter maps `interactive → user`) |
| `operator \| automation` | **Agents design only** |

Agent-caused transactions land in Activity, whose vocabulary is the first one. Introducing
`operator` adds a fourth dialect for the same concept.
**Recommend: `user | automation` for `AgentOrigin`, and `user | agent | automation | system`
for `AgentAuthorKind` — identical to `ActivityOrigin`.**

**`clientRequestId`.** The tree calls this `requestId` everywhere:
`DocumentCommandRequest.requestId`, `DocumentCreateReceipt.requestId`, Comments' receipts.
**Recommend: `requestId`.**

**`persona_digest`.** Ambiguous — Persona has two digests with different meanings:
`definitionDigest` (behaviour identity, stable across section selection) and `promptDigest`
(the rendered bytes, varies with section selection). "Which tasks used this persona's
behaviour" is a `definitionDigest` question; "which tasks got these exact bytes" is a
`promptDigest` question. **Recommend: store both, index on `(persona_id, definition_digest)`.**

### C7 · `lookup(requestDigest)` is unsatisfied *and* unnecessary — remove it

**Severity: highest-value finding in this review.**

`tools.md` requires every mutating target to implement `lookup(requestDigest)`, and D7 calls
it "the item most likely to be contentious", justified by:

> Document already stores `client_request_id` and `request_digest` for exactly this.

**Verified false.** Document stores `request_digest` on a receipt that is found by
`getSubmission(documentId, requestId)` or `getCreateSubmission(requestId)`. The digest is
used only to *compare* against a receipt already located by request id — it detects "same
request id, different body" (`IdempotencyMismatchError`). **There is no digest index and no
digest lookup anywhere in the tree.** Implementing D7 means adding a new index and a new
store method to every capability that wants to be a write target.

And it is not needed, because **Agents mints the request id**:

```ts
export interface DocumentCommandRequest {
  requestId: string;
  origin: DocumentOrigin;
  actorId?: string;
  command: DocumentCommand;
}
```

The adapter sends `requestId = "agent:<toolCallId>"` — deterministic, globally unique, and
allocated by Agents *before* the tool call row is committed. An identical re-dispatch then
replays Document's original result exactly, through the receipt mechanism that already
exists and is already tested.

So the unknown-outcome recovery branch becomes:

```text
found: tool call `dispatched`, no result
  → re-dispatch the identical command with the same requestId
      ├─ target replays its receipt  → it landed; write the result ref
      └─ target executes             → it had not landed; it lands now
```

This is exactly the reasoning that removed Document's delegated command claims on
2026-08-02: *"a retry after a crash between the external call succeeding and the local
receipt commit already replays the same result safely with no claim at all."*

**What it collapses.**

- **D7** stops being a requirement Agents places on other capabilities, and becomes:
  *"a mutating target must be idempotent by caller-supplied request id."* Document, Comments,
  and Templates already are. That is a much easier gate.
- **D8's third branch** (`outcome_unknown` → task waits for a human) becomes unreachable for
  compliant targets. Keep it only as the fallback for a target that is *not* request-id
  idempotent — which is now the definition of "cannot be a mutating target".

**The one caveat, and it is a real decision.** Re-dispatch *executes* if the call had not
landed. That is a retry, not a read. If you specifically want "find out what happened
without acting", you need `lookup`. For every command in the tree today, executing is the
desired outcome — the agent asked for it, policy allowed it, a human approved it, and it
never happened.

**Recommend: replay-by-re-dispatch.** Keep `requestDigest` — it still earns its keep for
approval binding, which is a completely separate job.

### C8 · The scope freeze has no generation fence, and the design never mentions it

Derived Outputs freezes **four** things before an expensive run: definition revision, head
revision, scope manifest, **and `knowledgeGeneration`**. The generation check exists because:

> A refresh that computed against generation *N* will not publish if the corpus is now at
> *N+1* — the answer would be grounded in evidence that no longer exists.

Agents freezes three. `resolvedSourceIds` are pinned, but the **windows behind those sources
are not** — a Connector sync or a General File replace mid-task silently changes what
`knowledge.retrieve` returns, and a citation recorded in step 3 may point at text that no
longer exists by step 9. Over a long task this is not hypothetical.

**Options.**

- **(a) Ignore.** Agents are interactive and seeing fresh material mid-task is arguably a
  feature, not a bug.
- **(b) Record, don't block.** Stamp `knowledgeGeneration` on each `retrieve` step, so
  evidence is attributable to a generation and a reader can see the corpus moved.
- **(c) Full fence.** Settlement refuses to complete if the generation moved. Wrong for
  agents — it would fail long tasks routinely for a reason the user cannot act on.

**Recommend (b).** It costs one integer per step and makes the audit record honest. The
design should at minimum state which of these it chose; right now it does not know the
question exists.

### C9 · `AgentToolResultRef.changeSetId` is Document-shaped

Only Document has ChangeSets. Comments, Templates, Persona, Structured Data, Context, and
Derived Outputs have revisions. A generic result ref should be:

```ts
interface AgentToolResultRef {
  readonly ok: boolean;
  readonly targetRevision?: number;
  /** Opaque target-side correlation id (Document ChangeSet, Activity transaction, …). */
  readonly targetRef?: string;
  readonly errorCode?: string;
}
```

`tools.md` line 224 and `canonical-model.md` line 354 both say "its own ChangeSet" where
they mean "its own accepted revision".

### C10 · Agent attribution does not reach the target as designed

`tools.md` requirement 2: *"The target's own ChangeSet records that an agent made it, with
the task and tool call id."*

Document records `origin: DocumentOrigin` and `actorId?: string`. There is no field for a
task id or a tool call id, and adding structured agent attribution to every producer is a
much larger change than the design implies.

**Options.**

- **(a) String convention.** `actorId = "agent:<taskId>:<toolCallId>"`. Zero target change.
  Attribution is greppable and joins back to the Agents row. Ugly but honest.
- **(b) Structured attribution on producers.** Add an optional `agentAttribution` to
  `DocumentCommandRequest` and to every other producer. Correct; touches every write target.

**Recommend (a) for v1**, stated explicitly so nobody assumes (b) exists. Note the design
already relies on `origin: "agent"` existing on the target, which it does for Document,
Comments, and Templates.

### C11 · `attention` is a cache and should be labelled one

Invariant 3 says `attention` is present iff `state === "waiting"`. But whether a task is
waiting is fully derivable from `questions WHERE state='open' AND required=1` and
`approvals WHERE state='pending'` — both of which have partial indexes precisely so that
query is cheap.

So `state`/`attention` are a denormalised cache over two tables. That is a defensible
performance choice (`task.attention` is the list a person works from), but the design
presents it as authority, and D16's own argument is that there must not be "a second place
where 'who are we waiting on' can disagree". Right now there are two, and the design does
not name the reconciliation rule.

**Recommend:** state that the tables are authoritative and `state`/`attention` are a
maintained projection written in the same transaction, and add a recovery check that
reconciles them. Same class as Document's `mutation_count` / `total_tokens` counters, which
`store.md` already justifies correctly.

### C12 · Policy evaluation only covers commands, not reads

`tools.md`'s evaluation pseudocode step 1 is "registry must resolve the **command**". But
reads also come from policy entries ("Every other read comes from a policy entry naming a
target's read command"), and `AgentTargetRead` is a separate type resolved by
`resolveRead`. The evaluation must try both and the entry must carry which one it is, or
`approval` semantics ("read entries ignore this") cannot be evaluated.

Small spec gap; mechanical fix.

## 4 · Processes and procedures

### The build staging deserves a rethink (D27)

D27 already admits stage 2 "is close to what Derived Outputs already does, so it may feel
like duplicated effort". It is closer than that. Stage 2 — read-only answering over a frozen
scope, with `knowledge.retrieve` bound as a tool and evidence validated against retrieval —
**is** `DerivedOutputService.refresh()`, minus the immutable revision chain and plus a
conversation.

There is a third option the design does not consider:

- **(a) As designed.** Reimplement retrieval + synthesis inside `agentRunner.ts`.
- **(b) Skip stage 2.** Go straight from stage 1 (task and exchange) to stage 3
  (multi-step runs), using a trivial read tool.
- **(c) Make Derived Outputs the first target.** Stage 2 becomes "an agent can `declare` and
  `refresh` a Derived Output and discuss the answer". Derived Outputs is registered as an
  `AgentTarget` with two commands and one read.

**(c) is materially better.** It proves the target registry, the policy check, the tool step,
and the commit-before-dispatch discipline — the *actual* risky machinery — with far less new
code, and it does it against a capability that is already idempotent by caller-supplied
idempotency key. The "mutation last" property of the staging survives, because declaring a
Derived Output mutates only Derived Outputs, which the task itself owns.

The trade: it makes the first milestone depend on the target registry, which the design
currently defers to stage 5.

### Activity publication (D26) — the machinery is already in the schema

D26 defers Activity publication citing Persona's precedent ("more machinery than a catalog
capability warrants"). But Agents' own schema already carries `ag_${prefix}_settlement_outbox`
for the Automation notification, written inside the settlement transaction and published
after commit. That is the same outbox shape Activity requires. The machinery cost is already
paid — what is left is a second `destination` and a publisher port.

And `ActivityOrigin` already includes `agent`, which exists for precisely this.

**Recommend:** one outbox table with a `destination` column (`activity` | `automation`),
publishing `agent.task.settled` from the first stage that settles tasks. Persona's
justification for deferring does not transfer, because Persona had no outbox at all.

### Persona's consumer laws are not restated, and Persona cannot enforce them

`persona/docs/flows.md` states six laws a consumer must keep. Agents is the first consumer.
The design honours most of them implicitly and mentions only the empty-scope guard.

| Persona law | In the design? |
| --- | --- |
| Resolve once per task, never per run | Implied by the freeze; not stated |
| Persist before the first model call | Stated (creation transaction) |
| The fragment never precedes the consumer's contract | Stated once, in the threat model |
| Union only — a persona may never narrow scope | Stated as the empty-scope guard only |
| Never substitute silently — unknown/deleted persona is an error | Not stated |
| Never log section text | Covered by the general logging rule |

**Recommend:** a short "Persona contract" section in `execution.md` listing all six with the
test that proves each, since Persona explicitly cannot enforce them.

## 7 · What is *not* wrong, and should not be re-litigated

Worth stating, because a review that only lists problems distorts the picture:

- The consumed-prefix rule (D12) is the best idea in the design. Steering, answers, and
  approvals all fall out of one immutable-prefix invariant, with no interrupt path. Keep it.
- Mutations as structured-output proposals rather than tool-loop handlers (D1) is correct and
  the reasoning is exactly right: reads are replayable, writes are not.
- `(runId, stepSeq)` replacing a separate stage-receipts table (D22) is strictly better than
  what Document does today.
- No `mode: "plan" | "action"` (D20) and no `taskKind` enum — expressing capability as policy
  data rather than as a union the runner interprets is the thing that makes one task machine
  cover everything.
- Terminal states absorbing (D14), no pause/resume (D21), and cancel-does-not-undo (D18) are
  all right and all cheap to get wrong.
- Target adapters in job wiring (D24) is the correct placement and matches
  `1-init/create/formula-name-resolver.ts`'s precedent for cross-capability translation.
